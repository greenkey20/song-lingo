# 작업 일지 (song-lingo)

이 문서는 하루 작업을 짧게 남기는 일지입니다. 사용자가 Notion 일일 기록에 복사해 쓰고, 강사님과의 면담 때 보는 용도입니다. 양식은 계획서 9장의 일일 기록(날짜 · 한 일 · 막힌 점 · 내일 할 일 · 질문)을 따르고, **면담이 있는 날은 전날 밤에 '강사님께 말씀드릴 것(브리핑)'을 미리 적어 둡니다**(면담 뒤에는 결정 사항 3줄을 채웁니다). 판단의 근거와 옵션 비교는 `프로젝트_안내_및_주제_검토.md`에 있고, 이 문서는 "무엇을 했고 각 파일이 무엇인지"만 적습니다.

> **AI가 쓴 코드를 이해하는 법**: 아래 파일 표의 **"수업과의 관계"** 열에서 '수업 코드 재사용'은 수업 자료로 복습하면 되고, **'수업에 없음'** 은 코드 주석과 이 표를 읽으며 따로 익힐 부분입니다. 새 코드에는 수업과 다른 부분을 주석에 `[수업에 없음]`으로 표시합니다.

| **API** | **Application Programming Interface**. 프로그램이 다른 서비스의 기능을 부르는 창구. 이 프로젝트에서 API를 부르는 곳은 OpenAI TTS 하나이고, 부를 때마다 **과금**됩니다(그래서 캐시에 있으면 부르지 않음). | `tts.py`(`tts.calls`로 호출 횟수 기록), `.env`의 `OPENAI_API_KEY` |
| **CPU · GPU** | **CPU = Central Processing Unit**(중앙 처리 장치, 일반 계산), **GPU = Graphics Processing Unit**(그래픽 처리 장치, 큰 모델 계산에 유리 **[일반 지식]**). 이 컴퓨터에는 GPU가 없어 모든 계산(Whisper, Demucs)을 CPU로 하고, 그래서 큰 모델과 분리가 느립니다. | `device="cpu"`, 검토 문서 15.2·15.4 |
| **WAV · PCM** | **WAV = Waveform Audio File Format**, 압축 없이 소리 숫자를 그대로 담는 파일 형식. **PCM = Pulse-Code Modulation**, 소리를 일정한 간격으로 재서 정수로 기록하는 방식이며 **PCM16**은 한 샘플을 16비트 정수로 기록한다는 뜻입니다. 이 프로젝트의 녹음은 스테레오 PCM16 wav입니다. | `recorder.save_wav`, `audio.py`(wav는 scipy, 그 밖의 형식은 `av`) |
| **스켈레톤 (skeleton)** | 계획서의 일부 기능을 앞당겨 **얇게 한 줄로 끝까지 관통**해 본 최소 동작 버전. 새 기능을 더하는 것이 아니라 "듣기 → 녹음 → 인식 → 채점 → 틀린 부분 표시"의 전체 흐름이 돌아가는지를 먼저 확인하는 것입니다. 발표 여부를 정하기 위해 11-01에 만들었고 지금의 `practice.ipynb`가 이어진 것입니다. | `experiments/skeleton/주말_스켈레톤_시연_계획.md`, `experiments/skeleton/발표_대본_초안_스켈레톤.md` |
| **반복 루프 (repetition loop)** | 인식기가 **같은 단어나 구절을 끝없이 되풀이해 적는** 현상. Whisper는 방금 자기가 쓴 글을 보고 다음 단어를 고르는데(자기회귀 **[일반 지식]**), 어렵거나 무음·반주가 많은 소리에서 같은 구절이 계속 가장 그럴듯하게 뽑히면 끝까지 반복합니다. 정답에 없는 단어가 수십~수백 개 **삽입(I)** 으로 세어져 WER이 1을 훨씬 넘습니다. 이 프로젝트에서는 삽입 40개 이상인 7건이 모두 고유 단어 비율 0.01~0.04, 4단어 연속 반복 0.98~1.00이었습니다 **[확인: 지표]**. 폴백이 이것을 끊어 주는 역할을 한다고 알려져 있고 **[일반 지식]**, 그래서 폴백을 끈 `temperature=0.0`에서 더 잘 생기는지 확인 중입니다 **[미확인]**. | `clip_compare`의 반복 지표(분석용), 노트북 ⑥ 아래 칸, 검토 문서 13.5 |
| **환각 (hallucination)** | 소리에 없는 말을 **만들어 적는 것**. 무음이나 음악만 있는 구간에서 Whisper가 말을 지어내는 경우가 알려져 있습니다 **[일반 지식]**. 반복 루프는 환각의 한 모양입니다. 강사님이 "모델이 무음까지 학습해서 문제가 될 수 있다"고 하신 것이 이것과 이어집니다. 그래서 무음을 거르는 VAD, 반주를 떼는 분리를 시험합니다. | 노트북 ⑥, 검토 문서 13.5, 15.2 |
| **온도 폴백 (temperature fallback)** | faster-whisper 기본 동작. 인식이 나쁘다고 판단하면(평균 로그확률이 낮거나 같은 말이 너무 반복되면) **온도(무작위성)를 0.0 → 0.2 → … → 1.0으로 올려 가며 무작위 샘플링으로 다시 인식**합니다. 반복을 끊는 데 도움이 되지만 같은 입력도 실행마다 결과가 달라질 수 있습니다. `temperature=0.0`을 주면 폴백이 꺼져 결과가 재현됩니다. | `stt.recognize(temperature=)`, 검토 문서 13.5 |
| **탐욕 디코딩 (greedy decoding)** | Whisper는 글자(토큰)를 **하나씩** 이어 붙여 문장을 만드는데, 매 단계에서 **가장 확률이 높은 한 개만 고르는** 방식입니다. 앞날을 내다보지 않고 지금 가장 좋아 보이는 것을 고르므로 "탐욕"이라고 합니다. 우리 설정 `beam_size=1`이 이 방식이고(후보를 여러 개 들고 가는 **빔 탐색**을 쓰지 않음), `temperature=0.0`은 무작위 샘플링까지 끈 것이라 **같은 입력이면 항상 같은 문장**이 나옵니다(노래 14구간을 경로로 2회 인식해 모두 같았음 **[확인]**). 다만 앞 글자가 바뀌면 그 뒤가 모두 따라 바뀌므로 **입력 소리가 아주 조금만 달라도 반주가 섞인 노래에서는 문장이 크게 달라질 수 있습니다**(우리 16 kHz 변환 배열 대 경로 입력, 14구간 중 10구간 **[확인]**, 원인 **[추정]**). 기본 설정도 처음에는 같은 방식으로 시작하고 결과가 나쁠 때만 온도 폴백으로 넘어갑니다 **[일반 지식]**. 검토 문서 16.4 |
| **리샘플링 (resampling)** | 소리의 초당 표본 수(표본화 주파수)를 바꾸는 것. 44.1 kHz·48 kHz 녹음을 Whisper가 쓰는 16 kHz로 줄일 때 씁니다. 방법마다 결과 파형이 아주 조금 다릅니다(우리 `audio.py`의 `scipy.signal.resample_poly` 대 faster-whisper의 PyAV). 코드 설명은 `audio.py` 맨 위 |
| **`bytes`·`BytesIO`** | `bytes`는 파일 내용을 **메모리에 통째로 담은 값**. 웹 화면의 업로드·브라우저 녹음은 파일이 아니라 이 형태로 들어옵니다. `io.BytesIO`는 그 bytes를 **파일처럼 읽게 해 주는 표준 도구**라서 파일 경로를 받는 코드(scipy·PyAV·faster-whisper)에 그대로 넘길 수 있습니다(이슈 #37) |

## 6. 코드·수업 복습 계획 (제안)

강사님이 "AI가 써준 코드는 이해해야 한다"고 했고 코드는 매일 쌓이므로, 몰아서 하지 않고 **작게 나눠 꾸준히** 소화하는 것을 목표로 합니다. 정규 수업 시간표는 제가 몰라서, 정식 수업 시간은 **새 수업 내용을 놓치지 않는 것이 우선**이라고 보고 기본 계획에서는 뺐습니다. 수업이 복습·실습 위주인 날 프로젝트와 겹치는 주제(예: Whisper 수업 날 `stt.py`)가 나오면 그때 연결해서 보면 좋습니다.

| 시간                               | 길이              | 할 일                                                                                                                                      |
| ---------------------------------- | ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 출퇴근·쉬는 시간(모바일 GitHub 앱) | 5~10분            | **한 파일의 맨 위 docstring**(역할, 수업과의 관계)과 함수 이름만 읽기. 일지 2-1 읽는 순서 표, 5장 용어 표 읽기. 코드가 길면 읽지 말고 표만 |
| 평일 저녁 작업 시작 전(데스크톱)   | 20~30분, 주 2~3회 | 그날 읽을 파일을 열어 **실행해 보며** 읽기(`python -c`로 함수 하나 불러 보기). 이해 안 되는 곳은 4장 '질문 후보'에 적기                    |
| 주말                               | 1~1.5시간         | 모듈 하나를 **소리 내어 설명해 보기**(발표 대본이 곧 복습). 막히는 곳이 이해가 덜 된 곳                                                    |

**기술부채를 줄이는 규칙**
- 새 파일을 만들면 일지의 파일 표와 읽는 순서 표에 한 줄을 추가합니다(이미 하는 중).
- 매일 일지에 "오늘 코드 이해 확인 질문 3개"를 적어 달라고 요청하면 다음 날 모바일에서 읽을 수 있습니다 *(요청하면 추가)*.
- 이해 안 되는 부분은 일지의 '질문 후보'에 적어 두고 면담이나 채팅에서 풉니다.
- 모바일 GitHub 앱은 `.py`와 `.md`는 읽을 수 있지만, 노트북(`.ipynb`) 렌더링은 불편할 수 있습니다 **[미확인]**. 모바일에서는 `.py`와 일지 위주로 봅니다.
