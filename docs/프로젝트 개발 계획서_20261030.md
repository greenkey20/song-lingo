## 1. 프로젝트 개요

### 목적(무엇을 달성하고자 하는가?)
- **한국어 사용자**가 외국어(영어·일본어·프랑스어 등) 노래에 나오는 문장을 프로그램에 직접 입력하면
- **TTS 기준 음성(선택한 TTS 음성의 발화)으로 듣고**, 
- **따라읽은 녹음을 음성 인식(STT)으로 확인**하거나 **받아쓰기**를 하고
- **정답 문장과의 오류율(WER/CER)** 과 **틀린 부분**을 피드백받는 연습 도구를 만듭니다.
- **LLM 서비스 API를 호출하여 연습 문장의 뜻, 연관 단어 및 표현**도 함께 학습할 수 있습니다.
- **프로토타입**이란 노트북에서 실제로 동작하는 **시제품**입니다. 핵심 흐름(듣기 → 읽기/받아쓰기 → 채점)을 직접 만들어 동작과 한계를 확인하는 것이 목표이고, 앱 배포·화면 완성도는 목표가 아닙니다(11-04: 웹 UI와 GitHub 배포는 하기로 했지만 핵심 흐름이 먼저입니다).
 
### 목표
- **Specific**: 연습 문장의 TTS 듣기 → 녹음 → STT → 정규화 → WER/CER → 틀린 부분 표시까지의 **한 가지 연습 흐름**을 완성
- **Measurable**: 문장 10개 × 3회 = **30건**을 오류 없이 처리하고 채점 결과를 손계산 5건과 대조
- **Achievable**: 필수 데이터(문장·녹음)를 **직접 만들 수 있고**, STT·TTS는 **사전학습 모델/API를 사용**하며, 구현 단계(L1→L2→L3)로 나누어 위험을 줄임
- **Relevant**: 수업에서 다룬 Whisper(활용, Whisper가 내부에서 만드는 **Log-Mel `(80, 프레임)`** 살펴보기 등), STT/TTS, 음성 전처리를 활용하고, 수업에서 다루지 않은 **WER/CER 평가를 자습으로 보완**해 연결
- **Time-bound**: **2026-11-11(수)까지 개발**(`L1` 11-04, `L2` 11-06, `L3` 11-10 완료 목표)

### 범위(포함될 사항)

  | 단계          | 내용                                                                                                                                                                                                                                                                                                                                                           |
  | ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | **L1 (필수)** | 영어 노래 문장 10개, **읽기 연습**: TTS 듣기 → 녹음 입력 → **녹음 입력 상태 점검(빈 파일·너무 작음·대부분 무음·클리핑 경고. 잡음 판별은 아님)** → STT(**기본 faster-whisper tiny**) → 정규화 → WER/CER(오류율) → 틀린 부분 표시                                                                                                                                |
  | **L2 (확장)** | **받아쓰기 모드**(TTS를 듣고 입력한 텍스트를 같은 채점으로 비교; 11-01 스켈레톤에서 앞당겨 구현), **재생 제어**(속도 0.75~1.25×·±5초·일시정지, HTML 플레이어로 시도), **연습 기록 저장·오류율 그래프**, **LLM으로 문장의 뜻·연관 단어·표현 제공**(직접 검수)                                                                                                                                   |
  | **L3 (심화)** | 아래 중 **1~2개 선택**: **(a) 노래 구간 인식 실험 및 음악·음성 분리**(낭독 vs 노래 인식 비교, 분리 전/후 비교), (b) **언어 1개 추가**(일본어 우선, TTS·STT 확인 후. 2번째 언어는 여유 시), 언어별 정규화 규칙, **(c) STT 신뢰 지표와 실제 오류의 관계 분석**, **(d) 직접 학습한 녹음 품질 분류기**, **(e) 잡음 견고성 실험**(합성 잡음 SNR별 인식 오류 변화, 실험 조건에 한정) |
  | **화면(UI)**  | 기본은 **노트북(`practice.ipynb`)**. **웹 UI는 Streamlit으로, 배포는 GitHub 저장소 기반으로 하기로 했습니다(11-02 면담 권장, 11-04 결정, 검토 문서 16.4·16.6).** 연습 로직은 `practice.py`의 함수로 분리되어 있어, 웹 UI는 같은 함수를 부르는 얇은 화면만 추가하면 됩니다. 앱은 `voice-ai`와 **별도 환경**에서 만듭니다(Streamlit이 요구하는 protobuf가 TensorFlow 2.16과 충돌, 이슈 #36). 공개 배포는 TTS 과금 때문에 접근 제한이 필요하며 PWA는 범위 밖입니다. |

### 1~4강(FFT·STFT·Mel) 활용 지점
| 어디에 | 무엇을 | 단계 |
| ------ | ------ | ---- |
| 16kHz 모노 변환 | 리샘플링(2강) | L1 |
| 녹음 입력 상태 점검 | STFT 프레임 에너지로 무음 비율, FFT로 저주파 웅웅거림·실제 대역폭 확인(3장 표) | L1 |
| 녹음 상태 확인 그림 | 스펙트로그램으로 눈으로 확인(참고 정보이며 평가 아님) | L1 선택 |
| Whisper 입력 이해 | Whisper 내부 Log-Mel 80과 4강 Log-Mel 40을 비교(수치를 직접 비교하지 않음) | 발표 연결 |
| (a) 노래 구간·음성 분리 | 낭독 / 노래 / 분리 후의 스펙트로그램 비교 | L3 |
| (e) 잡음 견고성 | 깨끗한 원본·10 dB·0 dB 스펙트로그램으로 잡음이 퍼지는 대역 확인 | L3 |

- **STT 경로**: 기본은 로컬 `faster-whisper tiny`이고 OpenAI STT는 로컬 실행 실패 시 대체 또는 비교 실험으로만 씁니다(TTS는 OpenAI로 고정).

## 3. 프로그램 구조

### 데이터 흐름
```text
[연습 문장 목록 sentences.csv]  (id, 언어, 문장, 한국어 뜻, 출처, 라이선스)
        │
        ├─① 듣기: 문장 → TTS(OpenAI) → 기준 음성 재생 (생성 음성은 캐시, `L2` HTML 플레이어로 속도·±5초·일시정지)
        │
        ├─② (a) 받아쓰기 (`L2`): 기준 음성 듣기(재생 제어) → 입력 텍스트 → 같은 정규화·WER/CER → 틀린 부분 표시
        ├─② (b) 학습 보조 (`L2`): 문장 → LLM(OpenAI 채팅 모델) → 뜻·연관 단어·표현 → 직접 검수 후 표시·저장
        │
        └─③ 말하기: 사용자 녹음(wav/m4a) → 16kHz 모노 → 녹음 입력 상태 점검(경고) → STT(faster-whisper 또는 OpenAI)
                                                          │ 인식 문장
                                                          ▼
         정답 문장 ──────────────▶ 정규화(언어별 규칙) ─▶ WER·CER 계산 ─▶ 틀린 부분 표시(역추적)
                                                          │
                                                          ▼
                                    연습 기록(CSV) 저장 ─▶ 오류율 그래프 (L2)
```

- **11-09 현행(웹 앱 기준)**: 위 흐름은 그대로이고 다음이 더해졌습니다. 문장은 웹 앱의 "내 문장"에서 직접 입력해 **줄마다 언어를 확인**한 뒤 연습하고, 내 곡·주변 음악 녹음에서 가사를 인식해 연습 줄로 만드는 "내 노래"가 있습니다. 연습 기록은 CSV가 아니라 **로그인한 사용자별로 서버 DB**에 저장되고(음원·녹음은 저장하지 않음), 한글 뜻·표현 설명은 버튼으로 요청하며, 발음 평가(Azure)는 사용자가 버튼을 눌렀을 때만 보냅니다. 모듈별 호출 관계는 `docs/module_structures_and_data_flow.md`에 있습니다.
- 문장은 `sentences.csv`에서 고르거나 노트북에서 **직접 입력**할 수 있습니다. 직접 입력한 문장은 기록에는 남기되 **평가 지표(10문장 × 3회)에서는 제외**합니다. 평가용 문장을 고정하는 이유는 같은 조건에서 반복 측정하고 손계산으로 검증하기 위해서입니다. `sentences.csv`의 10문장은 사용자에게 제공하는 **기본 예문**이면서 10문장 × 3회 통합 검증의 **고정 기준 데이터**를 겸하며, 문장별 목적과 30건 녹음의 목적·한계는 `experiments/WER, CER/연습_문장_데이터_설명.md`에 적었습니다.

#### 녹음 입력 상태 점검 방법 (`quality.py`, 기준값은 2026-11-01에 내 녹음으로 확정)
| 점검 | 계산 | 경고 기준(확정) |
| ---- | ---- | --------------- |
| 빈 파일·길이 | 샘플 수 ÷ SR | 길이 0.5초 미만 |
| 너무 작음 | 전체 RMS(dBFS), 최대 진폭 | RMS < −55 dBFS 또는 최대 진폭 < 0.02 |
| 클리핑 | **원본** 샘플 중 절댓값이 0.999 이상인 비율 | 1% 이상 |
| 대부분 무음 | STFT 프레임 에너지가 **가장 큰 프레임보다 35 dB 이상 낮은** 프레임의 비율 | 80% 이상 |
| 말한 시간 | (1 − 무음 프레임 비율) × 길이 | 1.0초 미만(대부분 무음이 아닐 때) |
| (참고) 저주파 웅웅거림 | FFT에서 80 Hz 이하 에너지 비율 | 참고 정보로만 표시 |
- 무음은 **절대 기준이 아니라 상대 기준**으로 판단합니다. 작게 녹음된 파일은 절대 기준(예: −60 dB)에서 전부 무음으로 잡힐 수 있기 때문입니다(10-30에 수업 제공 WAV를 0.02배로 줄여 확인).
- 이 점검은 **음량·무음·클리핑·말한 시간**만 봅니다. 잡음 여부는 판정하지 않습니다. 경고는 안내일 뿐 인식과 채점은 그대로 진행합니다.
- **확정 근거(11-01)**: 본인 녹음 6개(정상·멀리·작게·크게·짧게·침묵)와 소리 크기를 바꾼 실험에서 `faster-whisper tiny`는 소리 크기에 매우 강했습니다(RMS −74 dBFS까지, 샘플 16%가 잘려도 WER 0.000). 그래서 초안 기준(−40 dBFS, 0.05, 0.1%)을 완화하고, 실제로 인식이 깨진 '짧게 한마디' 녹음을 잡는 말한 시간 점검을 추가했습니다. 한 사람·한 마이크·조용한 환경 기준이며 잡음 환경은 시험하지 않았습니다(검토 문서 14.3, `quality.py` 맨 위).

#### 구현 순서
- 먼저 `practice.ipynb`에서 전체 흐름을 연결하고, 재사용·테스트할 함수부터 `.py`로 분리합니다. 
- **`scoring.py`는 반드시 분리**합니다.
- 11-01 기준 `scoring`·`tts`·`stt`·`audio`·`quality`·`align`·`visualisation`·`practice`·`report`가 모듈로 분리되었고, 노트북에는 `display`·`input`·`plt.show` 같은 화면 처리만 남았습니다. 노트북 없이 `practice.py`의 함수만 불러서 따라 읽기·받아쓰기·틀린 구간 그림까지 되는 것을 확인했습니다(검토 문서 10.8).

#### 영어 정규화 항목 (1일차에 코드로 고정)
- 유니코드 NFC 정규화 → 소문자화 → 구두점 제거 → 연속 공백 정리
- 축약형·숫자 표기(**11-03 결정, 검토 문서 13.4**): 정답과 인식 결과 **양쪽에 같은 규칙**으로 축약형을 펼치고(`we're`→`we are`, `don't`→`do not`; `'s`·`'d`는 제외) 0~99의 숫자 단어를 숫자로 통일(`twenty`→`20`)해서 채점하는 것을 **기본**으로 하고, 표기 차이까지 세는 **엄격 채점**도 인자(`unify=False`)로 선택할 수 있다. 결과를 보고할 때는 어느 쪽인지 적는다.
- **정답이 빈 문자열이면 계산하지 않고 오류로 처리**(분모 0)
- **WER은 1을 넘을 수 있으므로**(삽입이 많을 때, 예: 정답 1단어 vs 인식 3단어 → 2.0) 화면에는 `1−WER` 같은 "일치율"이 아니라 **오류율(WER·CER)과 치환·삭제·삽입 개수**로 표시
  
### 받아쓰기 모드와 재생 제어 (`L2`)
- **받아쓰기 흐름**: 문장 선택 → 기준 음성(캐시된 wav) 듣기 → 들은 내용을 입력(`input()`) → 정답과 **같은 `scoring.py`** 로 채점 → 오류율과 틀린 부분 표시 → 기록 CSV 저장. STT를 쓰지 않으므로 읽기 연습(L1)과 달리 **입력 텍스트가 곧 인식 결과**입니다.
- **재생 제어 구현**: wav는 **한 번만 생성해 캐시**하고, 노트북 셀에서 `IPython.display.HTML`로 `<audio>`와 버튼(처음부터 · −5초 · 재생/일시정지 · +5초 · 속도 0.75/0.9/1.0/1.1/1.25×)을 출력합니다. 브라우저 오디오의 `playbackRate`(속도), `currentTime`(위치 이동), `pause()`/`play()`를 쓰므로 **속도를 바꿔도 TTS API를 다시 호출하지 않고 원본 wav도 바뀌지 않습니다.**
- **동작 확인(5일차 시작 전 10분)**:VS Code에서 위 플레이어가 동작하는지 먼저 확인합니다 **[확인 필요]**. 동작하지 않으면 **기본 `IPython.display.Audio` 플레이어**(재생·일시정지·탐색 바만 제공)로 대체하고 그 사실을 기록합니다.
- **체크리스트(5항목)**: ① 속도별 재생 시간이 달라진다(0.75×면 약 1.33배) ② ±5초 이동이 된다 ③ 일시정지 후 위치가 유지된다 ④ 속도를 바꿔도 원본 wav가 그대로다 ⑤ Jupyter·VS Code 중 사용할 환경에서 동작한다.
- **범위 밖**: 피치를 유지하며 속도를 바꾸는 신호처리(Phase Vocoder)와 리샘플링 비교는 하지 않습니다(브라우저 재생 기능만 사용).

#### 11-01 기준 진행 현황과 일정 조정
- **끝난 것**: L1의 TTS·캐시, 녹음 → 16 kHz 모노 변환, 녹음 입력 상태 점검(기준값 확정), STT, 정규화·WER/CER·틀린 부분 표시, 읽기 연습 흐름. L2의 **받아쓰기 모드**와 문장 직접 입력. L3 시각화의 일부(**소리 그림, 틀린 구간 표시**). 브라우저 녹음 점검(spike).
- **남은 것**: L1 — 연습 문장 10개, 정규화 방침, 30건 녹음·검증. L2 — 재생 제어 플레이어, 기록 CSV, 오류율 그래프, LLM 뜻·표현. L3 — 선택 실험 전부. 공통 — README, 보고 자료. 이월 — 강사님께 확인할 항목(작업 일지의 질문 목록).
- **여유 시간 추정**: 남은 L1은 약 5h로 보여 2·3일차(8h)에 약 3h가 남고, 받아쓰기 구현분 약 1.5h를 더해 **약 4.5h의 여유**가 생기며 예비 시간 2h는 그대로입니다 **[추정]**. 평일 저녁은 식사와 수업 입장 전후 시간이 있고 컨디션이 일정하지 않아 실질 집중 시간이 4h보다 짧을 수 있으므로, 여유를 미리 쓰지 않고 4일차에 실제 진행 상황을 보고 쓸 곳을 정합니다.
- **11-03 방향 조정(L3-(a) 우선)**: 11-02 면담 뒤 [곡에서 음성·음악 분리 → 음성 STT → 그 문장으로 학습]을 개인 학습의 핵심으로 정했습니다. 11-03(연차 8h)과 주말(8h 이상)을 여기에 쓰고, **L2의 축소 여부는 4일차에 정합니다.** 11-03 스파이크에서 CPU 분리는 20초 구간에 약 65초(약 3.3배, 곡 1개 1회 **[확인]**)였으므로 구간 단위로 씁니다. 이슈는 #18(분리 스파이크·전/후 비교), #31(곡 → 연습 문장), #32(보컬 구간을 기준 음성으로)로 나눕니다. 일정·근거는 검토 문서 13.5, 날짜별 TODO는 작업 일지. **11-04 결정**: 노래 STT는 `medium` + 원곡 + VAD 끔 + 기본 설정입니다(다른 곡 6구간 검증에서 원곡 대 보컬은 확정하지 못했고, 분리는 학습자용 기준 음성을 위한 선택 기능으로 둠. 검토 문서 13.5·15.2, `노래_구간_비교_실험_절차.md` 12절).

### 프로젝트 범위 상 제외될 사항
- **상업 노래의 가사·음원 사용**(저작권, 공개 저장소)
  - 연습 문장은 **직접 작성한 예문**과 **사용 가능이 확인된 공개 문장**으로 한정
  - 11-03 조정: 저장소·이슈·문서에는 계속 올리지 않지만, **내 컴퓨터에서 로컬로 처리하는 개인 학습 도구**(영어 곡)와 **발표 시연에서 곡 1개를 로컬 재생**하는 것은 허용합니다(검토 문서 13.5). **11-04 변경**: 가사를 외부 API(TTS·LLM)로 보내는 것도 허용합니다(사용자 결정, 검토 문서 13.5). 가사로 만든 음성·설명 같은 결과물은 `data/`에만 두고 올리지 않습니다.
- **발음·억양·음정·박자 평가**
  - 전문 발음 평가는 범위 밖
  - STT는 문맥으로 **틀린 발음도 올바른 문장으로 고쳐 적을 수** 있는 바, 이 도구의 점수는 **발음 정확도가 아니라 "문장 인식 일치도"**
- 가수 목소리 분리, 가사 자동 추출을 **서비스 기능으로 완성**하는 것
  - L3-(a)는 **실험**이며 기능이 아님
  - 11-03 조정: 서비스(다수 사용자)로의 완성은 여전히 범위 밖이지만, 영어 곡에 한해 **개인 학습용 흐름**(곡 구간 → 보컬 분리 → 로컬 STT → 내가 고친 연습 문장)을 구현하고 실험합니다(이슈 #18·#31·#32).
- 다수 사용자 계정·서버 배포
  - 11-04: 웹 UI는 Streamlit + GitHub 배포로 하기로 했지만(검토 문서 16.4), 다수 사용자 계정 관리와 자체 서버 운영은 여전히 범위 밖입니다.
  - 11-01: Oracle Cloud 서버는 사양(ARM 4코어·RAM 23GB)과 `faster-whisper` 설치 가능 여부를 확인했을 뿐 배포하지 않았습니다.
- 노래 소리로 곡 검색, 실시간 스트리밍 인식
- 사전학습 모델의 **추가 학습(fine-tuning)**
- **녹음 한 개만 보고 잡음 여부나 SNR을 정확히 판정하는 기능**
  - L1 입력 상태 점검은 음량·무음·클리핑만 판단함
- **잡음 실험 결과를 실제 환경 전체로 일반화하는 것**
  - L3-(e)는 합성 흰 잡음(white noise)과 소수 문장으로만 실험하므로, 그 조건에서의 관찰로만 해석함
- **리샘플링·시간 신축 비교 같은 새 DSP 실험**
- **다른 화자 일반화 주장** 
  - 모든 녹음은 **본인 한 명**의 목소리로써, **다른 화자·기기에서도 같다고 주장하지 않음**
