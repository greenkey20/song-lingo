## ② Whisper anatomy ipynb

학습 자료로 적절함

이 노트북은 36개 셀로 구성되어 있어.

내가 확인한 주요 구성은 다음과 같아.

| 절    | 내용                            | 학습 가치                       |
| ----- | ------------------------------- | ------------------------------- |
| 1\~3  | 문제 정의, 모델 호출, 구현 계층 | Whisper와 faster-whisper의 관계 |
| 4     | 모델 파일 구조 분석             | Transformer 층과 파라미터       |
| 5     | Log-Mel 입력                    | 수업 STFT·Mel과 연결            |
| 6     | Encoder                         | CNN과 Self-Attention            |
| 7     | Decoder                         | 자기회귀 토큰 생성              |
| 8     | 실제 문제 분석                  | 환각, 반복, VAD, 온도 폴백      |
| 9\~11 | 확인 질문과 참고                | 발표 준비                       |

이 노트북에서 가장 좋은 부분은 모델 구조를 설명하는 데서 끝나지 않고 실제 프로젝트에서 겪었던 현상을 연결한다는 것이야.

예를 들어:

- 무음에서 문장이 생성되는 현상
- 같은 문장이 반복되는 현상
- 노래에서 VAD를 켰을 때 가사가 사라지는 현상
- 모델 크기에 따른 인식 결과 차이

이런 사례들은 발표에서 단순히 Transformer 구조를 설명하는 것보다 훨씬 설득력이 있어.

다만 발표 자료에 가져갈 때는 두 가지를 조정하면 좋겠어.

첫째, Whisper의 30초 입력과 처리 시간 설명을 조금 정교하게 해야 해.

현재 대본에는 다음과 같이 적혀 있어.

> 소리가 3초든 25초든 비용은 "30초 창이 몇 개냐"

이 표현은 인코더의 입력 길이와 계산량을 설명할 때는 적절하지만, Whisper 전체 처리 시간에 그대로 적용하면 부정확해.

- 인코더: 30초 창에 맞춰진 입력을 처리하므로 창의 입력 크기가 고정됨.
- 디코더: 생성하는 토큰 수에 영향을 받음.
- 전체 처리 시간: 창 개수뿐 아니라 생성 토큰 수, 디코딩 설정, 하드웨어 등에 따라서도 달라짐.

발표에서는 다음처럼 수정하는 게 정확해.

> Whisper는 입력을 30초 단위로 처리합니다. 짧은 음성도 고정 길이 입력으로 맞춰 인코더에 전달하기 때문에, 인코더의 입력 크기는 음성 길이에 따라 줄어들지 않습니다. 다만 전체 처리 시간은 디코더가 생성하는 토큰 수에도 영향을 받습니다.

둘째, 환각과 반복 현상의 원인을 단정하지 않는 것이 좋아.

현재 대본은 디코더의 언어 모델 특성과 자기회귀 구조를 근거로 설명하고 있어. 방향은 타당하지만, 특정 현상이 그 구조 하나 때문에 발생했다고 증명한 것은 아니야.

발표에서는 다음처럼 구분하면 돼.

- 확인: 무음 입력에서도 토큰이 생성되는 현상을 실험함.
- 확인: 디코더는 이전에 생성한 토큰을 다음 토큰 생성에 사용함.
- 해석: 입력 음향 정보가 부족할 때 언어적 패턴에 의존해 그럴듯한 문장을 생성할 수 있음.

이렇게 말하면 실험과 해석을 구분할 수 있어.

## ③ Demucs anatomy ipynb

이번 발표에서 가장 차별화할 수 있는 자료

77개 셀로 구성되어 있고, Whisper보다 훨씬 많은 분석 내용을 담고 있어.

특히 11월 10일에 추가한 부분이 중요해.

- 2-2절: LSTM이 단어와 음향 특징을 모두 처리할 수 있다는 점을 직접 실험
- 7-4절: CNN 출력이 Transformer에 전달되는 벡터 열이라는 점을 설명
- 8-4절: Self-Attention과 Cross-Attention의 계산 차이
- 8-5절: Positional Encoding
- 11-2절: 학습과 추론의 차이
- 12-2절: 이해 점검

이 중에서 발표에 활용할 가치가 높은 부분은 2-2, 7-4, 8-4야.

왜냐하면 이 부분이 바로 네가 최근에 질문했던 핵심 의문에 답하기 때문이야.

> 자연어 처리에서 배운 LSTM, Attention, Transformer가 어떻게 음악 신호를 처리하는가?

이 질문을 해결하기 위해 네가 실제로 같은 LSTM에 단어 임베딩과 음향 특징 벡터를 넣어 본 실험은 발표에 넣을 가치가 있어.

단순히 설명을 읽은 것이 아니라, 입력의 의미가 달라도 같은 신경망 층이 동일한 텐서 연산을 수행한다는 것을 직접 확인했기 때문이야.

다만 이 노트북에는 반드시 구분해야 할 부분이 있어.

현재 Demucs 노트북에서 수행한 작업

실행

사전학습된 HTDemucs 추론

혼합 음원을 넣고 네 개의 분리 결과를 생성했어.

분석

Demucs 학습 코드 확인

실제 학습 과정에서 정답 stem, loss, 역전파, optimizer가 어떻게 사용되는지 소스를 읽었어.

실행

작은 장난감 모델 학습

Demucs 자체가 아니라 단순화한 신경망을 학습해 손실과 가중치 변화의 원리를 확인했어.

따라서 이 파일은 Demucs를 직접 학습시킨 노트북이라기보다는 HTDemucs 구조 분석 및 학습 원리 탐구 노트북이라고 부르는 것이 정확해.

이 구분은 발표에서도 중요해. 사전학습 모델을 불러와 추론한 것과 모델 자체를 학습한 것은 다른 일이니까.

# 3. 발표 대본에서 수정하거나 보완할 기술적 사항

현재 대본은 전체적으로 잘 작성되어 있지만, 발표 전에 다음 사항은 정리하는 편이 좋아.

| 위치 | 현재 표현 또는 내용                               | 수정·보완 방향                                                  |
| ---- | ------------------------------------------------- | --------------------------------------------------------------- |
| 3장  | 계산은 모두 내 서버 안에서 수행                   | TTS, Azure 등 외부 서비스와 전송 정보를 정확히 구분             |
| 6장  | 3초든 25초든 비용은 30초 창 개수                  | 인코더 입력 크기와 전체 추론 시간을 구분                        |
| 6장  | 모델이 클수록 틀린 발음을 정답에 가깝게 고쳐 적음 | 모델 크기만으로 인과관계를 단정하지 않기                        |
| 7장  | CNN 4층 → Transformer 5층                         | 실제 HTDemucs의 두 가지 입력 경로와 텐서 변환을 시각적으로 제시 |
| 7장  | 파라미터 75%가 Transformer                        | 파라미터 비중과 실제 연산량·중요도가 같은 의미는 아님           |
| 7장  | SDR 21.6 dB 대 필터 3\~4 dB                       | 합성 입력 한정 결과라는 조건을 발표 화면에도 명시               |
| 8장  | 온도 0.0에서 반복 루프                            | 실험 설정과 관찰 결과로 표현하고 단일 원인으로 단정하지 않기    |
| 9장  | 단위 테스트 524개                                 | 실제 테스트 실행 시점과 테스트 범위가 무엇인지 질문에 대비      |

특히 7장의 75%라는 숫자는 흥미롭지만, 그 숫자만으로 Transformer가 모델 성능의 75%를 담당한다고 해석해서는 안 돼.

파라미터 수는 학습 가능한 숫자의 개수이고, 연산량이나 성능 기여도를 직접 나타내는 값은 아니야.

또한 3장의 개인정보 관련 문장은 실제 서버의 데이터 저장 동작과 일치하는지 발표 직전에 다시 확인하는 편이 좋아. GitHub README에는 로그인 사용자의 연습 문장과 인식 결과가 PostgreSQL에 저장된다고 설명되어 있어. 음성 파일 자체를 저장하지 않는다는 것과 연습 텍스트를 저장하지 않는다는 것은 다른 이야기야.

# 4. 지금 anatomy 내용을 완벽하게 이해해야 발표할 수 있을까?

아니야. 오히려 그 반대 방향으로 접근하는 게 효율적이야.

현재 네가 빠지기 쉬운 함정은 다음과 같아.

1. Demucs 노트북을 읽는다.
2. 모르는 수식이나 텐서 연산이 나온다.
3. 그 부분을 검색하고 리서치한다.
4. 새로운 용어가 등장한다.
5. 다시 새로운 개념을 공부한다.
6. 어느새 발표 준비 시간이 줄어든다.

이 과정 자체는 학습에 유익하지만, 발표 준비라는 목표에는 비효율적일 수 있어.

발표에서 설명할 내용과 개인적으로 더 깊이 공부할 내용을 분리해야 해.

예를 들어 HTDemucs의 Cross-Attention을 이해하려면 Query, Key, Value의 차원과 행렬 곱셈을 이해해야 해.

그런데 발표에서 반드시 설명해야 하는 것은 다음 정도야.

- 파형과 스펙트로그램이라는 두 표현을 사용한다.
- 각 경로의 CNN이 입력을 압축해 특징 벡터를 만든다.
- Transformer가 같은 경로 내부와 서로 다른 경로 사이의 정보를 결합한다.
- Decoder가 이를 다시 오디오 신호로 복원한다.

이 네 가지를 자기 언어로 설명할 수 있으면 발표의 기본 요건은 충족해.

Q·K·V의 구체적인 수식과 각 Attention Head의 내부 가중치까지 이해하는 것은 그다음 단계야.

## 내가 제안하는 이해 수준 3단계

Level 1. 발표 가능한 이해

필수

구조도 없이도 모델의 입력 → 처리 → 출력 흐름을 설명할 수 있음.

Level 2. 기술 질문에 답할 수 있는 이해

권장

텐서 shape, CNN, Attention, Decoder, 학습과 추론의 관계를 설명할 수 있음.

Level 3. 모델 내부를 연구하는 이해

장기 학습

Attention Weight의 실제 패턴, 각 Head의 역할, 학습된 가중치의 의미, 모델의 표현 학습을 분석할 수 있음.

11월 12일 발표를 위해서는 Level 1을 확실히 달성하고, Level 2의 핵심 항목을 가능한 만큼 확보하는 것이 목표야.

Level 3까지 이번 발표 전에 달성하려고 할 필요는 없어.

- 무엇을 이해했고, 무엇을 아직 이해하지 못했는지 구분한다.

특히 마지막 부분이 중요해.

이번 프로젝트에서 네가 얻은 가장 큰 성과가 반드시 새로운 딥러닝 모델을 개발했다는 데 있는 것은 아니야. 딥러닝 모델을 단순히 호출하는 데서 멈추지 않고, 그 모델의 입력·내부 구조·출력·한계를 추적하고 실제 서비스에서 검증했다는 점이야.
