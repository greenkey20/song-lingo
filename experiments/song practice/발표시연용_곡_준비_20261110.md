- 가사: 직접 작성한 영어 문장으로 구성
- 길이: 실제 시연에 필요한 구간 중심으로 생성
- 언어: 한 가지 언어로 명확하게 지정
- 보컬: 한 명의 보컬이 주도하도록 지정

특히 네 프로젝트는 기존 음악을 단순히 재생하는 것이 아니라, 음악을 입력 데이터로 받아 AI 모델을 거쳐 학습 자료로 바꾸는 것이 핵심이잖아.

따라서 시연용으로 직접 만든 곡을 사용하는 것은 프로젝트의 성격에도 잘 맞아.

다만 한 가지 주의할 점이 있어. Suno가 생성한 곡이라고 해서 원하는 가사를 언제나 정확하게 부르는 것은 아니야. Custom Lyrics에 직접 작성한 가사를 입력해도 실제 생성된 보컬이 단어를 생략하거나 변형할 수 있어. 최종 다운로드 파일을 반드시 Whisper로 테스트해야 해.

왜 영어를 추천할까?
세 가지 이유가 있어.

첫째, 발표자가 설명하기 쉽다.

시연 중에 다음과 같은 상황이 발생한다고 생각해 보자.

기준 가사:
We follow the lights through the city.

Whisper 인식 결과:
We follow the light through the city.

이 경우 lights가 light로 인식된 것을 보여 주면서 WER와 단어 대조를 설명할 수 있어.

청중도 영어 문장을 읽을 수 있으므로 결과를 바로 이해할 가능성이 높아.

둘째, 일본어보다 시연 과정의 부가 설명이 적다.

일본어에서는 히라가나 읽기, 가나·한자 표기, CER, pykakasi 등의 설명이 추가될 수 있어.

물론 이것은 SongLingo의 장점이기도 해. 하지만 15~17분 발표에서 모델 구조까지 설명해야 한다는 점을 고려하면 핵심 시연에서는 설명 부담을 줄이는 편이 좋아.

특히 현재 README에 기술된 것처럼 일본어와 영어가 혼합된 줄은 일본어 읽기 변환 과정에서 영어 부분이 별도로 처리되지 않아 글자 비교가 어긋날 수 있어.

셋째, 네가 이미 확보한 실험 결과와 연결하기 쉽다.

대본에서 사용하는 영어 예문, Whisper 모델 비교, WER 실험 결과를 발표 시연과 연결할 수 있어.

따라서 영어를 사용하면 시연 데이터와 사전에 준비한 실험 결과 사이의 일관성이 좋아져.
영어+일본어 J-pop은 왜 메인으로 추천하지 않을까?
이건 오히려 개인적으로는 가장 흥미로운 선택이야.

영어와 일본어가 섞인 J-pop은 SongLingo라는 프로젝트의 출발점과도 잘 어울려. 하지만 지금은 피하는 편이 좋아.

예를 들어 다음과 같은 가사가 있다고 해보자.
I follow the stars 君と歩いてく

이 문장은 언어 감지, 일본어 읽기 변환, 영어·일본어 혼합 문자열 비교, Whisper의 인식 결과 등 여러 문제가 얽혀 있어.

시연에서 문제가 발생하면 그것이 다음 중 무엇 때문인지 구분하기 어려워질 수 있어.
- 실제 보컬 발음
- Whisper의 언어 인식
- 가사 인식 오류
- 일본어 읽기 변환
- CER 계산
- 언어별 처리 로직
이번 발표에서는 이런 복잡성을 보여 주기보다 Demucs와 Whisper가 음악을 어떻게 처리하는지에 집중하는 편이 낫겠어.

일본어 J-pop은 발표 이후 두 번째 테스트 곡으로 남겨 두자.

3. Suno에서 어떤 스타일의 음악을 생성할까?
여기서 핵심은 장르보다 보컬의 명료도와 반주의 복잡도야.

Demucs와 Whisper가 각각 잘 작동할 수 있는 음악이어야 해.










A. Acoustic Indie Pop
가장 추천
- 보컬이 전면에 위치
- 기타·피아노·가벼운 드럼
- 비교적 단순한 악기 구성
- 가사 인식 결과가 명확하게 나올 가능성
Demucs 분리와 Whisper 인식 양쪽을 시연하기에 적절해.













B. Soft City Pop
- 베이스, 드럼, 신시사이저
- 적당히 풍부한 반주
- 보컬이 명확하다면 시각적으로 흥미로운 분리 결과
네가 좋아하는 J-pop 분위기를 살리기에 좋지만, 악기와 보컬이 겹치는 구간이 많아지면 인식이 어려워질 수 있어.













C. Electronic Synth Pop
- 신시사이저와 드럼의 비중이 큼
- 음향적으로 풍부한 소리
- Demucs 분리의 시각적 효과가 좋을 수 있음
다만 보컬에 이펙트가 많거나 반주가 매우 복잡하면 Whisper 인식에는 불리할 수 있어.



내 추천은 A와 B의 중간 정도야.

즉, 보컬이 앞에 있고, 기타·피아노·베이스·가벼운 드럼이 받쳐 주는 부드러운 팝이야.

너무 단순한 아카펠라로 만들면 Demucs를 사용할 이유가 약해지고, 반대로 악기가 너무 많으면 Whisper가 가사를 제대로 인식하지 못할 수 있어.

특히 README 기준으로 Demucs는 CPU에서 20초 구간을 처리하는 데 약 65초가 걸렸던 적이 있고, 전체 실행 환경에 따라 시간이 달라질 수 있어.

따라서 다음을 권장해.
- 발표에 사용할 음악 파일을 미리 업로드하고 구간을 정해 둔다.
- Demucs 분리 결과를 발표 전에 한 번 생성해 둔다.
- 보컬 분리 결과와 원곡 재생은 라이브로 보여 준다.
- 최종 따라읽기와 채점은 가능하면 라이브로 진행한다.
- 인터넷·마이크 문제가 발생할 때 사용할 결과 화면 캡처를 준비한다.
이렇게 하면 시연의 핵심인 실제 사용자 경험은 유지하면서 모델의 긴 처리 시간 때문에 발표가 지연되는 상황을 줄일 수 있어.

# 2. Anatomy를 어디까지 이해하고 발표해야 할까?

오늘 가장 중요하게 물어볼 질문

개인적으로는 이 질문이 오늘 면담에서 가장 중요하다고 생각해.

지금 네 상황을 구체적으로 보면 다음과 같아.

Whisper

- Log-Mel 입력의 크기와 의미를 확인했어.
- Encoder와 Decoder의 Transformer 구조를 추적했어.
- 모델 크기에 따른 층 수와 차원을 비교했어.
- 무음 환각, 반복 루프, VAD 관련 실험을 구조와 연결했어.
- 다만 내부 가중치와 Attention 패턴은 직접 확인하지 못했어.

Demucs

- HTDemucs의 실제 `forward()` 호출 흐름을 확인했어.
- Waveform과 Spectrogram 두 가지 입력 경로를 추적했어.
- CNN Encoder의 텐서 차원 변화를 관찰했어.
- Self-Attention과 Cross-Attention의 계산을 확인했어.
- 학습 코드와 Loss 구조를 읽었지만, 학습된 가중치가 실제로 무엇을 학습했는지는 확인하지 못했어.

즉, 두 노트북 모두 모델의 구조와 데이터 흐름을 상당히 구체적으로 분석했어. 그런데 네가 여전히 부족하다고 느끼는 이유는 구조를 읽고 이해하는 것과, 그 구조가 왜 그렇게 작동하는지 완전히 설명하는 것은 다르기 때문이야.

이 부분은 강사님의 피드백을 받는 것이 유익해.

이렇게 질문해 보자.

> 이번에 Whisper와 Demucs의 anatomy 노트북을 별도로 작성해서 모델 내부 구조와 데이터의 흐름을 추적했습니다. 단순히 모델을 호출해 사용하는 것을 넘어, 입력의 형태와 텐서 shape 변화, Encoder·Decoder·Attention의 역할까지 확인했습니다.
>
> 다만 학습된 가중치나 Attention Weight가 실제로 무엇을 학습했는지까지는 확인하지 못했습니다. 최종 발표에서 모델의 구조와 데이터 흐름, 제가 확인한 실험 결과를 설명하는 수준이면 적절할까요? 아니면 특정 개념을 더 깊게 파고들 필요가 있을까요?

이 질문은 강사님이 원하는 발표 깊이를 파악하는 데 직접적으로 도움이 될 거야.

그리고 답변이 "현재 수준이면 충분하다"라면, 더 깊이 공부하고 싶은 부분은 발표 이후 개인 학습으로 남겨 두면 돼.

# 3. Demucs 실험을 추가로 해야 할까?

질문 권장

이것도 오늘 질문할 만한 주제야.

현재 Demucs anatomy 노트북은 다음을 확인했어.

- 합성 입력으로 HTDemucs의 분리 구조를 관찰했어.
- 동일한 합성 입력을 고정 대역통과 필터와 비교했어.
- SDR을 측정했어.
- 학습과 추론의 차이를 확인했어.

하지만 노트북 자체의 합성 입력 실험과 실제 음악에서의 효과는 구분해야 해.

한편 프로젝트의 기존 실험에서는 실제 음악의 분리 전후 Whisper WER도 비교했지. 그리고 중요한 결과가 있었어.

| 실험            | 원곡    | 분리 보컬 |
| ------------- | ----- | ----- |
| tiny, 8개 구간   | 0.506 | 0.606 |
| medium, 기존 비교 | 0.177 | 0.257 |

즉, 보컬을 분리했다고 STT 성능이 반드시 좋아지는 것은 아니었어.

이 결과는 발표에서 오히려 좋은 이야기가 될 수 있어. 처음의 가설과 실제 실험 결과가 달랐기 때문이야.

다만 Suno로 새 시연곡을 만든다면, 그 곡을 추가 실험에 활용할지 고민할 수 있겠지.

강사님께는 이렇게 여쭤봐.

> Demucs는 합성 입력에서 구조와 분리 품질을 확인했고, 실제 음악에서는 분리 전후 Whisper 인식 결과가 오히려 나빠진 구간도 있었습니다. 발표 전에 새로 만든 시연곡으로 원곡과 분리 보컬의 WER를 동일한 설정으로 비교하는 실험을 하나 더 하는 것이 좋을까요? 아니면 기존 실험과 한계를 설명하는 것으로 충분할까요?

내 판단으로는 추가 실험을 한다면 한 곡, 한 구간만으로도 충분해. 새로운 대규모 실험을 시작할 필요는 없어.

# 4. 실험 결과와 기술적 해석을 어디까지 주장해도 될까?

질문 권장

이것도 질문의 가치가 높아.

현재 대본에는 실험에서 확인한 사실과 네가 구조를 바탕으로 해석한 내용이 함께 들어 있어.

예를 들어 Whisper의 경우:

- 무음·잡음에서 텍스트가 생성되는 현상을 관찰했어.
- Decoder가 자기회귀 방식으로 토큰을 생성한다는 것을 확인했어.
- 언어 모델 특성이 환각에 영향을 줄 수 있다고 해석했어.

Demucs의 경우:

- CNN이 시간·주파수 특징을 압축하는 과정을 확인했어.
- Transformer가 두 가지 표현의 특징을 결합하는 구조를 확인했어.
- 하지만 학습된 Attention이 실제로 무엇을 참고하는지는 확인하지 못했어.

이런 상황에서는 발표에서 어디까지가 실험 사실이고 어디부터가 해석인지 정확히 말하는 게 중요해.

질문은 다음과 같이 하면 돼.

> 이번 발표에서는 실험으로 직접 관찰한 사실과 논문이나 모델 구조를 바탕으로 해석한 내용을 구분하려고 합니다. 예를 들어 Whisper의 환각이나 Demucs의 Attention 역할에 대한 설명은 구조적인 해석을 포함합니다. 이런 경우 확인된 사실과 추정 또는 해석을 명시하는 방식이 적절할까요?

이 질문은 기술 발표의 신뢰성을 높이는 데 도움이 돼.
