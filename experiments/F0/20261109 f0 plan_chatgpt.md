# 2. F0 분석이 정확히 무엇을 보여 주는가?

## 2.1 F0의 물리적 의미

F0(Fundamental Frequency)는 성대 진동의 기본 반복 주파수와 관련된 값이야. 사람의 목소리가 유성음으로 발성될 때 성대의 진동이 주기적인 파형을 만들어.

예를 들어 F0가 200Hz라면 1초 동안 약 200번 진동한다는 뜻이야.

\\[ T=\frac{1}{F_0} \\]

따라서,

\\[ T=\frac{1}{200}=0.005\text{ s}=5\text{ ms} \\]

현재 SongLingo는 음성을 16kHz 모노 파형으로 변환해서 다루고 있지.

그러면 200Hz 목소리의 한 주기는 다음과 같은 샘플 수로 표현돼.

\\[ 16,000 \times 0.005=80 \\]

즉, 약 80개 샘플마다 비슷한 파형 패턴이 반복되는 거야.

F0에 따른 파형 주기 예시

# 100 Hz

1주기 = 10ms

16kHz에서 160 samples

# 200 Hz

1주기 = 5ms

16kHz에서 80 samples

## 2.2 F0가 없는 구간도 중요해

여기서 놓치면 안 되는 점이 있어.

모든 발화 구간에서 F0를 계산할 수 있는 것은 아니야.

예를 들어 영어 단어 `see`를 발음한다고 하자.

- `/s/`: 마찰음. 일반적으로 주기적인 성대 진동이 없어.
- `/iː/`: 모음. 성대의 주기적 진동이 나타나는 유성음이야.

따라서 F0 분석 결과는 대략 이런 형태일 수 있어.

```

0.01     /s/     NaN
0.02     /iː/    185 Hz
0.03     /iː/    190 Hz
0.04     /iː/    194 Hz

# 3. SongLingo에 넣을 F0 분석 알고리즘

내가 권하는 첫 번째 구현은 librosa의 pYIN이야.

## 3.1 왜 pYIN인가?

YIN은 음성의 주기성을 이용해서 기본주파수를 추정하는 알고리즘이야. 파형의 일정 간격만큼 밀어 보면서 얼마나 비슷한 패턴이 반복되는지 측정하고, 가장 그럴듯한 주기를 찾아.

pYIN(Probabilistic YIN)은 여기에 확률적인 후보 평가와 시간적 연속성 모델을 더한 방법이야.

공식 문서에서 설명하는 pYIN의 특성은 다음과 같아.

1. YIN으로 F0 후보와 후보별 확률을 계산해.
2. Markov chain 기반으로 시간에 따른 연속성을 고려해.
3. 각 프레임이 유성음인지 무성음인지도 추정해.

결과로 `f0`, `voiced_flag`, `voiced_probs`를 반환해.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://librosa.org\&sz=32)

이 세 가지 결과가 SongLingo에 유용해.

| 반환값         | 의미                                |
| -------------- | ----------------------------------- |
| `f0`           | 프레임별 F0 추정값(Hz)              |
| `voiced_flag`  | 해당 프레임을 유성음으로 판단했는지 |
| `voiced_probs` | 해당 프레임이 유성음일 확률         |

특히 사용자 녹음에 무음이나 자음 구간이 섞이므로 `voiced_flag`를 함께 쓰는 게 좋아.

## 3.2 구체적인 파라미터

현재 `audio.py`의 `audio.load_audio()`를 그대로 재사용하면 돼.

| 설정           | 제안값    | 설명                     |
| -------------- | --------- | ------------------------ |
| Sampling rate  | 16,000 Hz | 기존 음성 처리 규격      |
| `fmin`         | 65 Hz     | 탐색할 F0 최솟값         |
| `fmax`         | 500 Hz    | 탐색할 F0 최댓값         |
| `frame_length` | 2,048     | 한 번에 분석할 샘플 수   |
| `hop_length`   | 160       | 프레임 사이 이동 샘플 수 |

이 설정을 시간 단위로 바꾸면 다음과 같아.

\\[ \text{Frame duration}=\frac{2048}{16000}=0.128s \\]

\\[ \text{Hop duration}=\frac{160}{16000}=0.01s \\]

즉,

- 한 번의 F0 추정은 약 128ms 범위의 데이터를 이용하고,
- 10ms마다 다음 F0 추정을 수행해.

따라서 5초짜리 발화라면 대략 초당 100개, 약 500개의 F0 프레임을 얻을 수 있어.

처음부터 지나치게 복잡하게 설정하지 말고 이 값으로 시작하자. 단, 65\~500Hz는 모든 화자에게 맞는 절대적인 범위가 아니야. 실제 녹음에서 값이 상한이나 하한에 몰리는지 확인하고 조정해야 해.

```

시간에 따른 F0 변화

점선은 중앙 F0를 표시한 예시야. 실제 구현에서는 무성음 프레임을 비워서 구간을 끊어 그려야 해.

분석 결과 해석

- 발화 중 기본주파수의 중앙값은 185Hz야.
- 유성음으로 검출된 구간에서 F0는 주로 142\~236Hz 사이에 분포했어.
- 해당 범위는 약 8.8 semitones에 해당해.

  이 수치는 목소리의 음높이 변화를 설명하는 통계이지, 발음 정확도나 좋은 발음의 기준이 아니야.

여기서 실제로 표시할 항목은 네 가지면 충분해.

| 항목        | 사용자에게 설명할 의미                      |
| ----------- | ------------------------------------------- |
| Median F0   | 유성음 구간에서 관찰된 기본 음높이의 중앙값 |
| P10 F0      | 낮은 쪽 10% 지점                            |
| P90 F0      | 높은 쪽 90% 지점                            |
| Pitch range | P10\~P90 범위가 몇 semitones인지            |

왜 최소·최대가 아니라 P10·P90을 쓰냐면, F0 추정에는 octave error 같은 이상치가 생길 수 있기 때문이야. 극단값보다 백분위 범위가 전체 발화의 경향을 보여 주는 데 유리해.

반면 `voiced_ratio`는 첫 버전에서는 굳이 보여 주지 않아도 돼. 유성음 프레임 비중은 읽은 문장의 음소 구성과 쉼에 영향을 받기 때문에, 이 값을 유창성 점수처럼 해석하면 곤란해.

사용자 화면에 넣을 안내 문구는 다음과 같이 권장해.

> F0는 목소리의 기본적인 높낮이가 시간에 따라 어떻게 변화하는지 보여 줍니다. 무성음이나 무음 구간에서는 기본주파수가 표시되지 않을 수 있습니다. 사람마다 목소리의 높이와 발화 습관이 다르므로, 이 결과는 발음 점수가 아니라 음향 특성을 관찰하기 위한 참고 정보입니다.

# 5. 기존 프로그램의 어느 위치에 연결할 것인가?

이 부분은 저장소를 살펴보고 구체적으로 판단했어.

현재 `practice.read()`는 다음 역할을 해.

```
녹음 bytes
   ↓
quality.analyze()
   ↓
stt.recognize()
   ↓
scoring.evaluate()
   ↓
WER/CER 결과 dict
```

이 모듈은 이미 책임이 잘 분리되어 있어. 그러므로 F0 계산을 `practice.py`나 `scoring.py`에 넣지 않는 것이 좋아.

내가 권하는 데이터 흐름은 다음과 같아.

현재 채점 흐름

`rec.getvalue()`

브라우저 녹음 bytes

`practice.read()`

입력 상태 점검 → Whisper → WER/CER

기존 채점 결과 표시

추가할 F0 분석 경로

`pitch.analyze_f0(rec.getvalue())`

audio.load_audio() → librosa.pyin()

`visualisation.plot_pitch_contour()`

F0 그래프와 요약 통계

목소리 높낮이(F0) 분석 표시

구현할 파일의 역할은 다음과 같아.

| 파일                   | 변경 내용                            |
| ---------------------- | ------------------------------------ |
| `pitch.py`             | F0 계산 함수와 통계                  |
| `visualisation.py`     | F0 contour 그래프                    |
| `app/ui_practice.py`   | 기존 따라읽기 결과 아래 F0 분석 표시 |
| `tests/test_pitch.py`  | 합성 신호와 무음 테스트              |
| `requirements.txt`     | 분석 라이브러리 의존성               |
| `app/requirements.txt` | 배포 앱의 분석 라이브러리 의존성     |

특히 `app/ui_practice.py`에서는 지금의 채점 버튼 처리 흐름을 그대로 유지하면서, 채점에 성공한 경우 F0 계산을 별도로 수행하면 돼.

현재 코드가 `tts_path`가 있을 때만 기존 소리 그림을 만드는 구조라는 것도 중요해. F0 분석은 TTS 파일이 없어도 사용자 녹음만으로 계산할 수 있어야 하므로, `tts_path` 유무에 종속시키면 안 돼.

그리고 F0 계산이 실패해도 기존 WER/CER와 Azure 평가가 정상적으로 동작해야 해. F0는 부가 분석 기능이므로 기존 채점의 성공 여부를 좌우하면 안 돼.

# 8. 테스트는 어떤 데이터로 할 것인가?

여기가 부트캠프 수업과 연결되는 부분이야.

실제 사람의 목소리만으로 F0 추정이 잘 되는지 확인하면, 추정 알고리즘 자체가 맞는지 판단하기 어려워.

먼저 정답 주파수를 알고 있는 합성 신호로 검증하자.

## 테스트 1. 200Hz 사인파

수학적으로 200Hz라는 사실을 알고 있는 신호를 생성해.

\\[ x(t)=\sin(2\pi\cdot200t) \\]

16kHz로 샘플링해서 pYIN에 넣으면 추정 중앙값은 200Hz 근처여야 해.

같은 방식으로 120Hz, 250Hz 신호도 테스트하자.

| 입력 신호 | 기대 F0 | 검증 포인트                      |
| --------- | ------- | -------------------------------- |
| 사인파 A  | 120Hz   | 저음 추정                        |
| 사인파 B  | 200Hz   | 중간 범위 추정                   |
| 사인파 C  | 250Hz   | 상대적으로 높은 범위 추정        |
| 무음      | 없음    | F0를 0Hz로 잘못 표시하지 않는가? |

허용 오차는 초기 테스트에서 ±5\~10% 정도로 설정하고, 입력 길이와 알고리즘 조건에 따라 조정하면 돼. 이는 알고리즘의 보편적 정확도 보증이 아니라 네가 작성한 모듈의 회귀 테스트 기준이야.

## 테스트 2. 실제 사람의 녹음 3건

그다음 실제 사용자 녹음에서 다음을 확인해.

- 정상적으로 문장을 읽은 경우
- 중간에 긴 쉼이 있는 경우
- 작게 말하거나 주변 잡음이 섞인 경우

그래프에서 무성음과 무음 구간이 비어 있는지, 추정값이 갑자기 두 배 또는 절반으로 튀는 현상이 있는지를 살펴보면 돼.

## 테스트 3. 성능

이것도 중요해.

실제 서버는 Oracle VM이니까, F0 계산에 소요되는 시간을 확인해야 해.

- 3초 발화
- 5초 발화
- 10초 발화

정도로 측정하면 충분해. pYIN은 일반적인 단순 FFT보다 계산이 복잡할 수 있으므로, 실시간 처리를 전제로 하지 말고 채점 버튼을 눌렀을 때 한 번 계산하는 방식으로 시작하자.

# 9. F0 기능을 더 발전시키는 방향과 이번에는 하지 않을 것

현재 SongLingo가 지원하는 언어에는 영어·일본어·중국어·프랑스어·스웨덴어 등 여러 언어가 있어.

F0 분석은 다양한 언어에서 음높이 변화를 관찰하는 데 쓸 수 있지만, 언어별로 활용 목적이 다르다는 점을 기억해야 해.

| 언어     | F0의 활용 가능성                         |
| -------- | ---------------------------------------- |
| 영어     | 문장 억양, 강조, 음높이 변화 관찰        |
| 일본어   | 문장·단어의 피치 악센트 관찰 가능        |
| 중국어   | 성조에 따른 음높이 윤곽 관찰에 특히 유용 |
| 프랑스어 | 문장 억양과 리듬을 관찰하는 참고 자료    |

특히 중국어에서는 F0가 성조와 밀접하게 연결돼. 예를 들어 1성은 상대적으로 높은 평탄한 윤곽, 2성은 상승하는 윤곽처럼 나타나는 경향이 있어.

하지만 단순히 문장 전체의 F0 contour만 그렸다고 중국어 성조를 채점할 수 있는 것은 아니야. 각 한자의 발화 시간에 맞춰 음높이 윤곽을 정렬하고, 성조별 기준과 비교해야 해.

따라서 이번 버전에서는 언어별 발음 점수는 만들지 말고 언어와 관계없이 발화 전체의 F0 변화 그래프를 보여 주는 범용 음향 분석으로 한정하자.

그리고 원곡이나 반주가 섞인 음악 파일에 이 pYIN 모듈을 적용하지는 말자. pYIN은 단일 화자의 발화처럼 주된 피치가 하나인 신호를 대상으로 사용하는 게 적절해. 다성 음악에서는 여러 악기와 보컬의 주파수 성분이 섞여 결과를 해석하기 어려워.&#x20;

## 1. 기능 목적과 범위

- 사용자가 외국어 문장을 따라 읽고 녹음한 음성의 F0 contour를 계산한다.
- 시간에 따른 기본주파수(Hz) 변화를 그래프로 보여 준다.
- F0 중앙값, 10th percentile, 90th percentile, 10\~90 percentile 범위(semitones)를 요약한다.
- F0는 발음 정확도 점수가 아니라 음향 특성을 관찰하기 위한 참고 정보라고 명시한다.
- WER/CER 및 Azure Pronunciation Assessment의 기존 계산과 의미를 변경하지 않는다.
- 받아쓰기 모드에는 추가하지 않고 녹음이 있는 따라읽기 모드에만 추가한다.

## 3. 새 모듈 pitch.py

`pitch.py`를 새로 만든다.

- `audio.load_audio()`로 사용자 녹음 bytes를 16kHz 모노 파형으로 변환한다.
- librosa의 `pyin()`을 사용한다.
- 초기 파라미터:
  - `sr=16000`
  - `fmin=65`
  - `fmax=500`
  - `frame_length=2048`
  - `hop_length=160`
- 반환값:
  - `f0`
  - `times`
  - `voiced_flag`
  - `voiced_probs`
  - `valid` mask
  - `median_hz`
  - `p10_hz`
  - `p90_hz`
  - `range_semitones`
- 유성음이 충분하지 않으면 분석 불가 상태를 반환한다.
- 무음·너무 짧은 입력·잘못된 오디오 형식에서도 예외가 UI 전체로 전파되지 않도록 한다.
- NaN인 무성음 프레임을 0Hz로 바꾸지 않는다.
- librosa는 필요한 함수 안에서 지연 import하여 앱의 불필요한 시작 비용을 줄인다.

## 4. 시각화

기존 그래프 구조를 고려하여 `visualisation.py`에 F0 contour 그리기 함수를 추가한다.

## 5. UI 연결

`app/ui_practice.py`의 `practice_panel()`에서 기존 따라읽기 채점 버튼 처리 흐름을 확인한다.

기존 `practice.read()`와 WER/CER 결과 처리는 유지한다.

채점이 성공하면 기존 녹음 bytes(`rec.getvalue()`)를 F0 분석 함수에 전달한다.

F0 분석은 TTS 파일 유무에 종속되지 않아야 한다. 사용자 녹음만으로 계산할 수 있다.

F0 결과는 별도 Streamlit session_state key에 저장하고, 기존 소리 모양 비교 및 Azure 평가와 독립적으로 표시한다.

F0 계산에 실패해도 WER/CER와 Azure 평가에는 영향을 주지 않아야 한다.

건너뛰기 버튼을 누르면 F0 결과도 초기화한다.

## 6. 저장 범위

이번 구현에서는 F0 결과를 PostgreSQL에 저장하지 않는다.

- 신규 SQL migration을 만들지 않는다.
- `storage.py`와 `app/persist.py`의 저장 구조를 변경하지 않는다.
- `scoring` 또는 `azure` JSONB 컬럼에 F0 데이터를 넣지 않는다.
- 원본 녹음을 외부 서비스로 전송하지 않는다.
- F0는 현재 앱 실행 흐름 안에서 계산하고 현재 연습 결과 화면에만 표시한다.

여기서 P10과 P90은 이상치의 영향을 줄여서 발화 중 주로 나타난 음높이 범위를 나타내려는 값이야.

그리고 semitones는 음악에서 음높이 차이를 나타낼 때 사용하는 단위야.
\[
\Delta p = 12\log_2\left(\frac{F_0^{end}}{F_0^{start}}\right)
\]

175Hz에서 223Hz로 변했다면 약 +4.2 semitones야.

이 숫자는 음악적 음높이 차이로 해석할 수 있고, 사용자가 자신의 음높이가 얼마나 변했는지 직관적으로 이해하는 데 도움을 줘.

중요한 것은 +4.2가 +2.0보다 더 좋은 발음이라는 뜻은 전혀 아니라는 사실이야.

단, 영어의 모든 의문문이 반드시 상승 억양을 가져야 하는 것은 아니야. 문장 유형과 대화 상황, 방언 및 화자의 말하기 습관에 따라 억양이 달라질 수 있어. 따라서 SongLingo에서는 "질문이면 F0를 올려라" 같은 규칙으로 채점하면 안 돼.

시나리오 B. 중국어의 성조를 연습하는 사용자
F0는 특히 중국어처럼 성조가 뜻을 구분하는 언어에서 교육적 의미가 더 커질 수 있어.

SongLingo는 이미 중국어(zh)를 지원하잖아.

중국어의 보통화에는 네 가지 주요 성조가 있어.
중국어 성조의 기본 음높이 윤곽
1성 · mā

2성 · má

3성 · mǎ

4성 · mà


이 도식은 성조의 전형적인 윤곽을 단순화한 교육용 예시야. 실제 발화의 윤곽은 문맥, 발화 속도, 연속 발음에 따라 달라져.
예를 들어 중국어 학습자가 mā와 má의 차이를 연습한다고 하자.

사용자가 F0 그래프를 보면서 다음 사항을 확인할 수 있어.
- 첫 번째 발화는 음높이가 비교적 유지되는가?
- 두 번째 발화는 음높이가 상승하는가?
- 실제 발음을 다시 들어 봤을 때 두 성조의 차이가 귀에도 분명하게 들리는가?
이것은 F0 분석을 학습에 활용하는 좋은 사례야.

다만 이 단계는 SongLingo의 첫 번째 F0 구현 범위보다 더 발전된 기능이야. 성조를 단어별로 정확히 평가하려면 글자·음절별 시간 정렬, 문맥에 따른 성조 변화, 해당 성조의 목표 패턴이 필요해.

현재의 문장 전체 F0 그래프만으로 중국어 성조 점수를 산출하면 안 돼.

다만 이번 일정에서 시간이 부족하다면, 첫 번째 구현은 단일 발화 그래프와 요약 통계까지만 만들고, 직전 발화 비교는 확장 기능으로 남겨도 돼.

5. 한 가지 더 발전시킬 수 있는 아이디어: TTS와 내 목소리의 F0 contour 비교
SongLingo의 장점은 이미 표준 발음 TTS를 제공한다는 점이야.

따라서 나중에는 표준 발음과 내 녹음의 F0 contour를 같은 그래프에 나타낼 수도 있어.

하지만 여기에는 중요한 기술적 주의점이 있어.

TTS의 F0가 120Hz이고 사용자 목소리의 F0가 220Hz라고 해서 사용자가 잘못 발음한 것은 아니야.

두 사람은 본래 목소리 높이가 다를 수 있기 때문이야.

따라서 두 목소리의 절대 Hz를 비교하기보다는, 각 화자의 중앙 F0를 기준으로 상대적인 높낮이 변화(semitone)를 비교하는 편이 더 타당해.

예를 들어 다음처럼 표현할 수 있어.
\[
p(t)=12\log_2
\left(\frac{F_0(t)}{\mathrm{Median}(F_0)}\right)
\]

이렇게 하면 각 화자의 기본 음높이를 제거하고 상대적인 억양 변화 형태를 살펴볼 수 있어.

두 녹음의 발화 속도와 시간 정렬이 다르기 때문이야. 문장 전체의 시작과 끝을 단순히 0~100%로 맞추는 것만으로 각 단어의 억양을 정확하게 비교할 수는 없어.

단어 및 음절별로 정렬한 다음 상대적인 F0 contour를 비교해야 제대로 된 학습 자료가 될 수 있어.

6. Claude Code에 전달할 구현 명세
지금까지 정리한 내용을 Claude Code에 전달할 수 있도록 하나의 구현 요청문으로 묶었어.

이 문서는 단순히 "F0를 계산해 줘"라는 요청이 아니라, SongLingo에서 사용자가 무엇을 보고, 어떻게 해석하고, 다음 발화에서 무엇을 연습할 수 있어야 하는지를 정의한 거야.
SongLingo — F0 분석 결과 UI/UX 및 학습 활용 설계
1. 목적
SongLingo의 따라읽기 결과 화면에 F0(Fundamental Frequency) 기반 음향 분석을 추가한다.

목적은 발음 정확도 점수를 추가하는 것이 아니다.

사용자가 자신의 목소리에서 음높이가 시간에 따라 어떻게 변화하는지 관찰하고, 발화 의도와 억양의 관계를 생각하며, 다음 발화에서 의도한 억양을 연습하도록 돕는 것이다.

F0는 발음 정확도를 직접 평가하지 않는다. 따라서 0~100점이나 좋음/보통/나쁨 등급을 부여하지 않는다.
2. UI 위치
기존 app/ui_practice.py의 practice_panel()에서 따라읽기 결과를 표시하는 흐름을 유지한다.

기존 표시 요소:
1. WER/CER 결과
2. 단어 대조
3. 틀린 구간 표시
4. Azure Pronunciation Assessment
5. 소리 모양 비교(파형·FFT·STFT·Log-Mel)
이들 아래에 새로운 섹션을 추가한다.

섹션 제목:
목소리 높낮이 분석 · F0

설명:
"내 목소리의 기본적인 높낮이가 시간에 따라 어떻게 변화했는지 확인해 봐."
3. 사용자에게 보여 줄 항목
A. 중앙 F0
- 유성음 프레임에서 계산한 F0 중앙값
- 단위 Hz
- 설명: "이번 발화에서 주로 관찰된 목소리 높이"
B. 일반적인 음높이 범위
- F0의 10th percentile
- F0의 90th percentile
- 예시: 170~225Hz
- 설명: "이번 발화의 유성음에서 주로 나타난 음높이 범위"
- 필요하면 semitone 범위도 함께 표시할 수 있다.
C. 시간에 따른 F0 contour
- X축: 발화 시간(초)
- Y축: F0(Hz)
- 무성음·무음 구간은 선을 연결하지 않고 비워 둔다.
- 중앙 F0를 참고선으로 표시한다.
- 기존 SongLingo의 초록색 테마를 사용한다.
D. 문장 앞·뒤 구간의 음높이 변화
초반과 후반의 유성음 F0 중앙값을 구한다.

예시:
- 앞부분: 175Hz
- 마지막 부분: 223Hz
- 변화: +4.2 semitones
계산:
12 * log2(마지막 F0 중앙값 / 앞부분 F0 중앙값)

해당 값은 억양 변화를 관찰하는 참고 정보이지, 발음 점수가 아니다.

각 구간에 충분한 유성음 프레임이 없으면 해당 요약값을 표시하지 않는다.
E. 분석 결과 해석
예시 문구:

"마지막 발화 구간에서 음높이가 상승하는 경향이 관찰돼."

"앞부분과 마지막 부분의 유성음 F0 중앙값을 비교한 결과야. 발음의 정답 여부를 판정하는 점수는 아니야."

F0 변화량에 따라 상승·하강·유지 경향을 표현할 수 있으나, 특정 임계값에 따른 자동 등급이나 발음 정답 판정은 만들지 않는다. 임계값을 사용할 경우 실험적 휴리스틱임을 명시한다.
4. 사용자의 다음 학습 행동
결과 화면에 아래와 같은 학습 활용 안내를 표시한다.
1. 표준 발음을 다시 들어 보면서 문장의 의미와 억양을 확인한다.
2. 자신의 녹음을 다시 들으면서 그래프의 음높이 변화를 살펴본다.
3. 특히 문장 끝이나 강조하려는 단어에서 음높이가 어떻게 변하는지 확인한다.
4. 동일한 문장을 다시 녹음하면서 의도한 억양을 재현해 본다.
질문형 문장에는 상승 억양이 나타나는 경우가 있지만, 모든 의문문이 상승 억양을 갖는 것은 아니다. 언어와 대화 맥락에 따라 다르므로 보편적인 정답 규칙으로 사용하지 않는다.
5. 기술적 주의
- audio.load_audio(source, sr=16000)을 재사용한다.
- pYIN의 f0, voiced_flag, voiced_probs를 활용한다.
- 무성음 프레임의 F0는 NaN으로 유지한다.
- 0Hz로 바꾸거나 무성음 구간을 발음 오류로 취급하지 않는다.
- F0 분석 실패가 WER/CER·Azure 평가에 영향을 주지 않도록 한다.
- fmin/fmax는 기본값으로만 취급하며 실제 사용자 음성에서 탐색 범위가 적절한지 확인한다.

- polyphonic music 및 반주가 섞인 입력에는 이번 F0 발화 분석 기능을 적용하지 않는다.

그리고 두 번째 질문에 대한 답은 가능하고, 오히려 단어별 시간 정보를 F0 contour와 함께 보여주는 편이 학습 측면에서 더 유용하다는 거야. 다만 F0와 단어의 시간 정보를 어떻게 연결하는지가 중요해.

## 1. F0 contour만 보여주는 것의 한계

예를 들어 사용자가 다음 문장을 읽는다고 해보자.

> Are you ready?

사용자가 확인을 요청하는 의문문으로 발화하려고 했지만, 실제로는 평서문처럼 억양 변화 없이 읽었다고 가정하자.

F0 분석 결과가 다음과 같을 수 있어.

| 구간      | F0                |
| --------- | ----------------- |
| 문장 초반 | 175Hz             |
| 문장 후반 | 177Hz             |
| 변화량    | 약 +0.2 semitones |

이 데이터만으로 알 수 있는 건 다음과 같아.

- 문장 초반과 후반의 기본주파수가 거의 동일하다.
- 발화 마지막 부분에서 뚜렷한 음높이 상승이 관찰되지 않는다.

하지만 여기에는 중요한 정보가 빠져 있어.

사용자가 어떤 억양으로 발음하려고 했는지에 대한 기준이 없다는 거야.

F0는 관찰된 음향 특성이지, 그 자체가 정답이나 오답을 판정하는 기준은 아니거든.

### 그렇다면 무엇이 추가되어야 할까?

내 생각에는 SongLingo에서 F0 분석을 학습 기능으로 활용하려면 다음 세 가지가 연결되어야 해.

① 발화 의도 및 문장 맥락

사용자가 어떤 상황과 의미로 문장을 읽어야 하는지 이해한다.

② 참고 발화의 F0 contour

TTS 또는 다른 기준 음성에서 문장 전체의 억양 흐름을 관찰한다.

③ 사용자 발화의 F0 contour

실제 녹음에서 사용자의 음높이 변화를 추출하고 참고 발화와 비교한다.

예를 들어 다음과 같은 식이지.

| 구분        | 초반 F0 | 후반 F0 | 변화량         |
| ----------- | ------- | ------- | -------------- |
| 참고 음성   | 175Hz   | 223Hz   | +4.2 semitones |
| 사용자 음성 | 175Hz   | 177Hz   | +0.2 semitones |

이 경우 사용자는 단순히 자신의 F0가 거의 변하지 않았다는 사실만 보는 게 아니야.

참고 발화에서는 마지막 부분에서 음높이가 상승했는데, 자신의 발화에서는 그 변화가 거의 없었다는 점을 발견할 수 있어.

단, 여기서도 주의할 점이 있어.

- TTS의 억양이 모든 상황에서 유일한 정답은 아니야.
- 의문문이라고 항상 끝을 올려야 하는 것도 아니야.
- 화자의 억양, 지역, 발화 상황, 문장의 화용적 의미에 따라 적절한 억양은 달라질 수 있어.

따라서 UI에서는 '정답 억양'보다는 참고 발화와 내 발화의 차이라는 표현이 적절해.

또한 TTS와 사용자의 절대 F0를 그대로 비교하면 안 돼. 사람마다 기본 음높이가 다르기 때문이야.

예를 들어 TTS의 중앙 F0가 180Hz이고 사용자의 중앙 F0가 130Hz라고 해서 사용자의 음높이가 잘못된 것은 아니지.

비교하려면 각 음성의 중앙 F0를 기준으로 다음처럼 상대적인 음높이 변화를 계산하는 방법이 있어.

\\[ F0\_{\text{relative}}(t) = 12\log_2\left(\frac{F0(t)}{\operatorname{median}(F0)}\right) \\]

이렇게 하면 Hz가 아니라 중앙값으로부터 몇 semitones 높거나 낮은지를 비교할 수 있어.

## 2. F0 contour의 x축에 단어를 표시할 수 있을까?

가능

이건 기술적으로 충분히 구현할 수 있어.

핵심은 F0 분석 결과와 단어별 시간 정보를 결합하는 것이야.

현재 SongLingo에는 이미 관련 기능이 있어.

네 프로젝트에서 `practice.py`의 `locate_errors()`는 녹음과 TTS 음성에 대해 단어 단위 인식 정보를 활용해 오류 구간을 찾고 있어. 그리고 발음 평가 화면에서도 오류 구간의 시간 정보를 시각화하고 있지.

즉, SongLingo에는 이미 시간축에 단어 정보를 연결하는 기반이 있어.

### 2-1. 어떤 데이터가 필요한가?

예를 들어 Whisper가 사용자 발화를 다음과 같이 인식했다고 해보자.

| 단어  | 시작 시간 | 종료 시간 |
| ----- | --------- | --------- |
| Are   | 0.10초    | 0.35초    |
| you   | 0.36초    | 0.55초    |
| ready | 0.56초    | 1.25초    |

한편 pYIN은 10ms 간격으로 F0를 추정한다고 가정하자.

| 시간   | F0    |
| ------ | ----- |
| 0.10초 | 175Hz |
| 0.11초 | 176Hz |
| 0.12초 | 174Hz |
| ...    | ...   |
| 1.20초 | 220Hz |
| 1.21초 | 223Hz |

이 두 데이터를 시간축에 맞춰 결합하면 돼.

- Whisper: 어떤 단어가 어느 시간에 발화되었는가?
- pYIN: 해당 시간에 음높이가 어떻게 변했는가?

두 데이터는 서로 다른 분석 결과지만, 동일한 녹음 파일을 기준으로 하기 때문에 시간축을 공유할 수 있어.

Hz

semitones

개념도: 녹음된 단어의 시작·종료 시점을 F0 그래프의 시간축에 투영한 모습이야. 실제 F0는 무성음 구간 등에서 끊겨 표시될 수 있어.

사용자가 관찰할 수 있는 내용

- Are: 상대적으로 낮은 음높이에서 시작
- you: 음높이가 완만하게 상승

단어를 단순히 그래프 밑에 나열하는 데 그치지 않고, 단어의 시작·종료 시간을 세로 경계선으로 표시하고 각 단어 구간을 배경 영역으로 구분하는 게 좋아.

그러면 사용자는 어느 단어를 발음할 때 음높이가 상승했는지 시각적으로 확인할 수 있어.

## 3. 그런데 단어별 표시가 실제 학습에 의미가 있을까?

나는 의미가 있다고 판단해. 특히 문장 전체의 F0 변화만 보는 것보다 학습자가 자신의 발화를 구체적으로 관찰하기 쉬워져.

다만 활용 목적은 언어마다 조금씩 달라.

| 학습 대상 | 단어별 F0의 활용                         |
| --------- | ---------------------------------------- |
| 영어      | 문장 강세, 억양 변화, 강조되는 단어 관찰 |
| 중국어    | 성조의 음높이 패턴 관찰                  |
| 일본어    | 단어 내 모라의 높낮이 패턴 관찰          |
| 한국어    | 문장 억양과 강조·감정 표현 관찰          |

예를 들어 영어 문장에서는 다음과 같은 질문에 답할 수 있어.

- 어떤 단어에서 음높이가 크게 변했는가?
- 문장 마지막 단어에서 상승 또는 하강이 관찰되는가?
- 강조하려는 단어에서 음높이 변화가 있었는가?

중국어에서는 조금 더 직접적인 활용이 가능해.

중국어 성조는 음절별 F0 변화와 밀접한 관련이 있으므로, 단어별 또는 음절별 F0 contour를 표시하면 학습자가 성조의 흐름을 관찰하는 데 도움이 돼.

단, 일반적인 단어 단위 구간만으로는 충분하지 않을 수 있어. 중국어는 한 단어가 여러 음절로 구성될 수 있으므로, 실제 성조 학습에는 음절 단위의 시간 정렬이 더 적합해.

### 한 가지 기술적 한계: Whisper의 단어 타임스탬프는 정답 타임스탬프가 아니야.

여기서 구현 시 주의해야 할 문제가 있어.

Whisper의 word timestamp는 음성 인식과 정렬을 통해 추정한 시간 정보야. 정확한 음소 경계나 발화 시작·종료 시점을 항상 정밀하게 알려주는 것은 아니야.

특히 다음과 같은 상황에서는 문제가 생길 수 있어.

- 단어를 생략한 경우
- 단어를 잘못 발음해서 Whisper가 다른 단어로 인식한 경우
- 단어 사이를 지나치게 빠르게 연결해서 발음한 경우
- 녹음 품질이 좋지 않은 경우

이럴 때 단어 구간이 실제 발화와 어긋날 수 있어.

따라서 MVP에서는 다음 원칙을 추천해.

1. 사용자 녹음에 대한 Whisper의 단어별 시간 정보를 사용한다.
2. 각 단어의 시작·종료 시간에 맞춰 F0 그래프에 표시한다.
3. 인식된 단어를 기준으로 표시하며, 정확도가 불확실한 정렬은 과도하게 해석하지 않는다.
4. 나중에 필요하면 forced alignment를 도입해 기준 문장과 실제 발화의 정렬을 개선한다.

그리고 `ready`라는 단어의 F0를 분석한다고 해서 `r`, `e`, `a`, `d`, `y` 각각의 발음 정확도를 알 수 있는 것은 아니야. 단어 구간의 F0는 해당 시간 동안의 기본주파수 변화를 나타낼 뿐이야.

## 4. SongLingo에 적용한다면 어떤 형태가 가장 좋을까?

내가 추천하는 건 F0 분석을 독립적인 점수 기능으로 만들기보다는, 기존 발음 분석 결과를 보완하는 시각적 자기 관찰 기능으로 추가하는 거야.

구현 우선순위는 다음과 같이 잡겠어.

1단계: F0 contour + 단어 구간

MVP 추천

사용자 녹음의 F0 contour를 표시하고 Whisper word timestamp를 이용해 단어별 구간을 함께 표시해.

2단계: TTS 참고 억양과 비교

TTS 음성의 F0도 추출하고, 중앙 F0 기준 상대 semitone으로 변환해 사용자 음성과 비교해.

3단계: 단어·음절 단위 피드백

언어별 특성에 따라 영어의 강세, 중국어의 성조, 일본어의 pitch accent 등을 더 구체적으로 관찰할 수 있게 발전시켜.

## 1. 먼저 12 log₂ 공식으로 무엇이 달라지는지 보자

기존에 이야기한 공식은 다음과 같아.

\\[ R_s(t)=12\log_2\left( \frac{F0_s(t)}{\operatorname{median}(F0_s)} \right) \\]

여기서 \\(s\\)는 화자(TTS 또는 사용자)를 의미해.

핵심은 각 음성의 중앙 F0를 기준점인 0 semitone으로 만드는 것이야.

예를 들어 다음과 같이 TTS와 사용자의 목소리 높이가 다르다고 해보자.

| 구분       | TTS          | 사용자          |
| -------- | ------------ | ------------ |
| 중앙 F0    | 190Hz        | 135Hz        |
| 특정 구간 F0 | 213Hz        | 151.5Hz      |
| 상대적 음높이  | +2 semitones | +2 semitones |

절대적인 주파수는 다르지만 중앙 F0보다 약 2 semitones 높다는 점은 동일해.

이런 식으로 변환하면 각 화자의 목소리 자체가 높은지 낮은지는 비교에서 제외하고, 기본 음높이를 기준으로 얼마나 상승하거나 하강했는지를 비교할 수 있어.

- 0 semitones: 해당 음성의 중앙 F0와 동일
- +2 semitones: 중앙 F0보다 2 semitones 높음
- -2 semitones: 중앙 F0보다 2 semitones 낮음
- +12 semitones: 중앙 F0의 2배

따라서 그래프의 y축은 더 이상 Hz가 아니야.



권장 y축

`Relative pitch (semitones from speaker median)`



사용자에게도 이 의미를 설명하면 돼.

## 2. 두 가지 그래프 방식 비교

### A. 하나의 그래프에 두 contour를 겹쳐서 표시

최종 추천

예를 들어 `"Are you ready?"`라는 문장을 읽는다고 해보자.

상대 억양 비교 · 예시 데이터

각 음성의 중앙 F0를 0 semitone으로 정규화한 개념도개념도일 뿐 실제 TTS·사용자 녹음에서 추출한 데이터는 아니야. 실제 그래프에서는 무성음 구간의 F0가 비어 있을 수 있어.

이런 형태라면 사용자는 바로 알아볼 수 있어.

- TTS: 문장 후반으로 갈수록 음높이가 상승한다.
- 내 녹음: 문장 후반에도 음높이가 거의 변하지 않는다.
- 차이: 특히 `ready` 구간에서 두 contour의 상승 패턴이 다르다.

그래프에서 두 선을 직접 비교할 수 있으므로 사용자가 별도로 두 그림을 번갈아 해석할 필요도 없어.

다만 위 개념도처럼 시간축이 정렬되어 있다는 전제가 필요해.

### B. 두 그래프를 나란히 또는 위아래로 배치

이 방식도 가능하지만, 두 음성의 시간축을 일치시킬 수 없다면 오히려 더 적절한 선택이야.

상대 억양 비교

참고 TTS

내 녹음

두 음성의 각 발화 길이를 0\~100%로 환산한 별도 표시 예시야. x축의 같은 위치가 반드시 같은 단어를 의미하지는 않아.

이 방식의 장점은 구현이 단순하다는 거야. 각 발화의 길이를 0\~100%로 변환하고, 동일한 y축 범위에서 두 그래프를 그리면 돼.

하지만 단점도 명확해.

TTS에서 `ready`가 발화의 60\~100% 구간에 있고, 사용자는 `ready`가 75\~100% 구간에 있다면 두 그래프의 동일한 x 위치가 같은 발음 구간을 가리키지 않을 수 있어.

따라서 전체적인 상승·하강 추세를 관찰하는 데는 쓸 수 있지만, 특정 단어의 억양을 비교하는 용도로는 한계가 있어.

그리고 y축을 Hz로 표시한 다음 '절대적인 음높이는 무시하세요'라고 안내하는 방식은 추천하지 않아. 애초에 변환된 상대 semitone을 y축에 써서 사용자가 잘못된 해석을 하지 않도록 하는 게 좋아.

## 3. 내가 최종 추천하는 방식: 단어 순서에 맞춘 단일 중첩 그래프

여기서 한 단계 더 생각해 보자.

TTS와 사용자는 같은 문장을 말하더라도 발화 속도가 다르고, 단어마다 차지하는 시간이 달라.

그러므로 단순히 두 음성의 전체 시간을 0\~100%로 정규화하는 것보다 같은 단어가 그래프의 같은 x축 위치에 오도록 정렬하는 방식이 더 유용해.

예를 들어 문장을 세 단어로 나눠보자.

| 공통 x축 구간 | 단어     |
| -------- | ------ |
| 0\~1     | Are    |
| 1\~2     | you    |
| 2\~3     | ready? |

TTS의 `Are`는 0.1\~0.4초, 사용자의 `Are`는 0.2\~0.7초에 발화했다고 가정해보자.

각 단어 구간을 같은 x축 구간으로 변환하는 거야.

- TTS `Are`: 실제 시간 0.1\~0.4초 → x축 0\~1
- 사용자 `Are`: 실제 시간 0.2\~0.7초 → x축 0\~1

이렇게 하면 두 음성의 발화 시간이 달라도 같은 단어를 같은 구간에서 비교할 수 있어.

수학적으로는 각 단어 구간의 시간을 다음과 같이 변환하면 돼.

\\[ x(t)=i+\frac{t-t\_{start}}{t\_{end}-t\_{start}} \\]

- \\(i\\): 문장에서 해당 단어의 순서(0부터 시작)
- \\(t\_{start}\\): 해당 음성에서 단어가 시작한 시각
- \\(t\_{end}\\): 해당 음성에서 단어가 끝난 시각

이렇게 변환한 x좌표에 앞서 계산한 상대 F0를 y좌표로 사용하면, 하나의 그래프에 두 contour를 겹쳐 그릴 수 있어.

단, 이 방법은 각 단어의 발화 길이를 동일하게 늘이거나 줄이는 것이기 때문에 단어 내부의 세밀한 음소 타이밍이나 발화 속도 차이까지 비교하지는 못해. 그것은 별도의 분석 영역이야.

5. 무성음·누락 단어·짧은 녹음에 대한 예외 처리

여기서 중요한 범위 제한이 있어.

- 우선 영어처럼 공백 기반 단어 구분이 가능한 문장을 대상으로 구현하는 게 좋아.
- 중국어·일본어 등은 단어 분리 및 음절 단위 정렬이 별도로 필요할 수 있어.
- 강제 정렬(forced alignment), 음소 단위 비교, 자동 발음 점수는 이번 MVP에서 제외해.
- 기존 오류 구간 분석에서 이미 실행한 Whisper 단어 인식을 다시 반복하지 않도록 결과를 공유하는 구조로 바꾸는 게 좋아.

따라서 단순히 그래프 하나를 그리는 것보다는 작업량이 있지만, 기존 코드를 재사용하면 오늘\~내일의 집중 개발 범위로 충분히 현실적이야. 다만 실제 구현·테스트를 거치기 전까지 완료를 보장할 수는 없어.

## 5. 최종 UI에서 사용자가 읽어야 할 안내 문구

그래프 아래에는 다음 정도의 설명을 넣는 걸 추천해.

참고 음성 vs 내 목소리 · 상대 억양 비교

두 음성의 기본 음높이 차이를 줄이기 위해 각각의 중앙 F0를 기준으로 상대적인 음높이를 표시해요.

같은 단어에서 두 선이 어떻게 상승하거나 하강하는지 살펴보세요. 선의 흐름이 다르다면 해당 단어를 다시 듣고, 목소리의 높낮이 변화를 의식하면서 한 번 더 발음해 보세요.

이 그래프는 억양의 음향적 차이를 관찰하기 위한 참고 자료예요. TTS의 억양이 유일한 정답은 아니며, 발음의 정확성이나 자연스러움을 직접 채점하지 않아요.

그리고 결과에 따라 다음과 같은 학습 행동으로 연결할 수 있어.

예를 들어 TTS는 `ready`에서 +4 semitones 상승하고 사용자 녹음은 +0.5 semitones 상승했다고 해보자.

사용자는 다음 순서로 연습할 수 있어.

1. TTS의 `ready` 구간을 다시 듣는다.
2. 자신의 `ready` 구간을 다시 듣는다.
3. 그래프에서 두 음성의 상대적인 음높이 변화 차이를 관찰한다.
4. 문장의 의도에 맞춰 마지막 단어의 억양을 의식하면서 다시 녹음한다.
5. 새 녹음의 contour를 이전 결과와 비교한다.

여기서 중요한 건 +4 semitones가 반드시 정답이라는 뜻이 아니라는 점이야. 사용자가 자기 발화를 분석하고 수정할 구체적인 단서를 얻는 것이 목표야.

최종 결론: SongLingo에는 `화자별 중앙 F0 정규화 + 단어 단위 시간 정렬 + 하나의 그래프에 두 contour 중첩`을 추천해. 단순히 두 그래프를 나란히 보여주는 것보다 같은 단어에서 억양의 흐름을 직접 비교할 수 있기 때문이야. 이번 개발에서는 영어 중심으로 이 기능을 먼저 완성하고, 다른 언어의 음절·성조 단위 분석은 후속 과제로 분리하는 게 합리적이야.

## 1. 각 항목의 구체적인 UI/UX 제안

현재 `app/ui_practice.py`를 기준으로 설명할게. 확인한 소스에는 이미 이 항목들의 화면 요소와 보조 설명이 상당히 구체적으로 구현되어 있어. 따라서 기존 기능을 없애거나 새로 만드는 것보다 역할을 명확하게 구분하고 배치와 표현을 정리하는 것이 우선이야.

### ① 문장 인식 결과 · Whisper

가장 먼저 보여줄 결과

현재 `_show_result()`가 보여주는 핵심 결과 카드야.

유지할 요소:

- WER: 단어 오류율
- CER: 글자 오류율
- S/D/I: 바뀜(Substitution), 빠짐(Deletion), 더해짐(Insertion)
- 녹음 품질 상태: 음량, 무음 구간, 클리핑
- 인식한 문장과 인식 소요 시간

여기서 가장 중요한 건 이 결과가 발음 정확도 점수가 아니라 문장 인식 일치도라는 점이야.

현재 `app/explain.py`의 `read` 설명에도 명시되어 있어. Whisper는 문맥을 이용하기 때문에 사용자가 잘못 발음했더라도 의도한 단어를 올바르게 인식할 수 있거든.

그러므로 결과 카드의 제목은 다음을 추천해.

문장 인식 일치도 · Whisper

그리고 카드 바로 아래에 다음 안내를 유지하거나 추가해.

> 이 결과는 녹음된 음성을 문자로 인식한 뒤 기준 문장과 비교한 오류율이야. 발음 정확도 자체를 평가하는 점수는 아니야. 잘못 발음한 단어를 Whisper가 문맥으로 보정했을 수도 있어.

녹음 품질 칩은 점수와 별도로 유지해. 음량이나 클리핑 경고는 결과 해석에 필요한 입력 상태이지, 발음 점수가 아니니까.

### ② 단어·글자 대조

현재 시각 요소를 그대로 유지하는 편이 좋아.

- 위쪽: 기준 문장
- 아래쪽: 사용자 음성의 인식 결과
- 정상적으로 일치한 부분: 일반 텍스트
- 바뀐 부분: 보라색 + 물결 밑줄 + `바뀜`
- 빠진 부분: `빠짐`
- 추가된 부분: `더해짐`

즉, 색상뿐 아니라 밑줄과 텍스트 라벨을 같이 사용한다는 현재 설계가 적절해.

다만 제목은 언어에 따라 유연하게 바꿔야 해.

- 영어 등 공백으로 단어를 구분하는 언어: 단어 대조
- 일본어·중국어 등 현재 채점 로직이 글자 단위로 처리하는 언어: 글자 대조

현재 `_show_result()`의 `languages.uses_spaces()` 분기를 그대로 활용하면 돼.

현재 소스에서는 `_show_result()` 바로 다음에 TTS와 사용자 녹음의 재생 컨트롤이 배치되어 있어. 위치도 적절하므로 유지하길 추천해.

표준 발음을 먼저 듣고 자신의 발화를 이어서 들을 수 있게 하는 거야. 특히 아래의 틀린 구간과 F0 그래프를 보기 전에 실제 소리를 먼저 듣는 학습 흐름이 만들어져.

### ④ 틀린 구간 확인

현재 `_show_error_spans()`와 `visualisation.plot_error_spans()`가 담당하는 부분이야.

이 기능은 유지해야 해. 단어 대조가 무엇이 달랐는지 알려준다면, 틀린 구간은 그 차이가 음성의 어느 시간대에 발생했는지 알려주니까.

현재 그래프의 구조도 의미가 있어.

- 왼쪽: 표준 발음(TTS)
- 오른쪽: 내 녹음
- 첫 번째 행: 파형
- 두 번째 행: STFT
- 세 번째 행: Log-Mel
- 각 단어의 시작 위치에 단어 이름 표시
- 오류 덩어리는 `[1]`, `[2]`처럼 동일한 번호를 양쪽에 표시
- 단어가 없는 쪽은 점선으로 표시

여기서 반드시 유지할 주의 문구가 있어.

> 구간은 Whisper가 추정한 단어 시간이라 정확한 강제 정렬이 아니야. 오류가 발생한 위치를 보여주는 참고 정보이며, 발음이 틀린 원인까지 진단하지는 않아.

그리고 오류가 하나도 없다면 현재처럼 다음 안내를 보여주면 돼.

> 인식 결과가 기준 문장과 같아서 표시할 구간이 없어.

오류가 없을 때 억지로 그래프를 보여줄 필요는 없어.

### ⑤ 억양 흐름 비교 · F0

이번에 추가할 핵심 기능

이 항목은 `틀린 구간 확인` 다음에 배치하길 추천해.

오류가 발생한 위치를 확인한 다음, 발화의 음높이 흐름을 살펴보는 순서야.

추천 제목은 다음과 같아.

목소리 높낮이 비교 · F0 contour

주요 시각 요소는 다음과 같아.

- 하나의 그래프에 TTS와 사용자 F0 contour 중첩
- TTS는 초록색, 사용자 음성은 보라색 등 기존 색상 규칙 활용
- y축: 상대 음높이(semitones from speaker median)
- x축: 단어 순서에 맞춰 정렬한 발화 구간
- 무성음 구간은 0Hz로 처리하지 않고 선을 끊어 표시
- 단어별 구간을 구분하고 단어 이름을 표시

그래프 밑에는 다음 설명을 추가해.

> 각 음성의 기본 음높이 차이를 줄이기 위해 중앙 F0를 기준으로 상대적인 음높이를 표시해. 같은 단어에서 두 선이 어떻게 상승하거나 하강하는지 관찰해 봐. 이 그래프는 억양의 음향적 차이를 살펴보기 위한 참고 정보이며, 발음 점수는 아니야.

특히 여기서도 'TTS의 contour가 정답'이라는 인상을 주면 안 돼. TTS는 비교 기준이지 유일한 정답 억양이 아니야.

단어 정렬이 불확실하면 정확하게 정렬된 것처럼 표시하지 않는 것도 중요해. Whisper 시간 정보는 추정값이므로, 대응이 불가능한 단어 구간은 빈 구간으로 남기거나 비교할 수 없다는 안내가 있어야 해.

### ⑥ Azure 발음 평가

현재 `_show_azure()`의 구조를 유지하되, 명칭과 위치를 조금 수정하는 걸 추천해.

현재 제목은 `표준 평가 · Azure 발음 평가`인데, 나는 Azure 발음 평가 · 외부 서비스 · 선택을 추천해.

Azure가 독립적인 발음 평가 모델을 제공하는 건 맞지만, 이를 모든 발음의 보편적인 정답이나 절대적인 표준 점수로 오해하지 않도록 하기 위해서야.

현재 기능에서 유지할 요소:

| 점수 카드 | 의미                 |
| ----- | ------------------ |
| 정확도   | 음소 발음의 일치 정도       |
| 유창성   | 단어 사이 쉼의 자연스러움     |
| 완성도   | 기준 문장에서 발음된 단어의 비율 |
| 운율    | 억양·강세·속도·리듬        |
| 종합    | Azure가 산출한 종합 점수   |

점수 카드 다음에는 기존과 같이 단어별 정확도 표시를 유지하고, 음소별 IPA 분석은 펼쳐서 볼 수 있도록 해.

중요한 것은 실행 전 안내야.

> 버튼을 누르면 내 녹음과 기준 문장, 언어 정보가 Microsoft Azure Speech로 전송돼. 표준 발음(TTS) 음성은 전송하지 않아. Azure의 발음 평가 모델로 내 발음을 분석하는 선택 기능이야.

이 기능은 사용자가 직접 버튼을 눌렀을 때만 실행되어야 해. 기존의 외부 전송 동의 흐름을 바꾸면 안 돼.

| 파형      | 시간에 따른 진폭                | 말한 구간과 쉼, 발화 타이밍               |
| FFT     | 전체 소리의 주파수별 크기           | 어떤 주파수 성분이 포함되어 있는지. 시간 정보는 없음 |
| STFT    | 시간에 따른 주파수별 파워           | 특정 주파수 성분이 언제 나타났는지            |
| Log-Mel | 시간에 따른 Mel 주파수 영역의 로그 파워 | 음성 인식 모델이 활용하는 음향 특징의 형태       |

이 항목에서 두 가지 주의사항이 있어.

첫째, 현재 파형은 두 음성의 최대 진폭을 각각 0.9로 맞춰서 표시해. 그러므로 그래프에서 실제 음량이 더 크거나 작다고 해석하면 안 돼.

둘째, FFT의 가장 큰 주파수 봉우리가 반드시 기본주파수(F0)는 아니야. 배음이나 다른 성분이 더 크게 나타날 수 있기 때문이야. F0 분석은 별도의 pYIN 분석 결과를 사용해야 해.

또한 현재 파형·STFT·Log-Mel은 두 음성을 나란히 놓고 실제 시간축으로 그려. 단어별 정밀 정렬 결과를 보여주는 것은 아니므로, 같은 x 위치에 있는 두 소리가 같은 단어라고 단정하지 않도록 설명을 조정하는 게 좋아.

## 2. 최종 UI에서 가장 중요한 설계 원칙

세 가지는 꼭 구분해야 해.

첫째, 점수와 관찰 데이터를 분리해.

WER/CER와 Azure는 각자의 방식으로 산출된 평가 결과야. 반면 F0, 파형, FFT, STFT, Log-Mel은 음향 특성을 관찰하는 데이터야. 둘을 같은 종류의 점수처럼 나열하면 안 돼.

둘째, 핵심 피드백과 심화 분석을 분리해.

사용자가 모든 음향 분석 그래프의 의미를 알아야만 따라읽기 연습을 할 수 있는 구조는 피해야 해. WER/CER, 단어 대조, 오류 위치, F0까지는 기본 피드백으로 보여주고, Azure와 음향 심화 분석은 추가 기능으로 인지할 수 있도록 해.

셋째, 오류가 없더라도 학습할 수 있어야 해.

WER/CER가 0%라고 해서 발음과 억양까지 완벽하다는 뜻은 아니야. 따라서 오류 구간이 없어도 F0 비교는 실행할 수 있어야 해. 이게 F0를 추가하는 중요한 이유 중 하나야.

참고한 현재 소스는 [app/ui_practice.py](https://github.com/greenkey20/song-lingo/blob/main/app/ui_practice.py?utm_source=chatgpt.com), [app/explain.py](https://github.com/greenkey20/song-lingo/blob/main/app/explain.py?utm_source=chatgpt.com), [visualisation.py](https://github.com/greenkey20/song-lingo/blob/main/visualisation.py?utm_source=chatgpt.com), [web_practice.py](https://github.com/greenkey20/song-lingo/blob/main/web_practice.py?utm_source=chatgpt.com), [align.py](https://github.com/greenkey20/song-lingo/blob/main/align.py?utm_source=chatgpt.com)야.

# SongLingo — 따라읽기 결과 UI/UX 최종 구성 및 F0 통합

## 1. 작업 목표

현재 따라읽기 연습에서 `채점하기`를 누른 후 표시되는 결과 화면을 사용자 학습 흐름에 맞게 재구성해줘.

이번 작업의 목적은 다음과 같아.

1. 기존 WER/CER 결과와 단어 대조 기능을 유지한다.
2. 기준 문장과 사용자 녹음을 다시 듣고 오류 발생 위치를 확인할 수 있도록 한다.
3. 새로 추가하는 F0 분석을 통해 TTS와 사용자 음성의 상대적인 억양 변화를 비교할 수 있도록 한다.
4. Azure 발음 평가와 음향 시각화의 역할을 명확하게 구분한다.
5. 핵심 피드백과 심화 분석을 구분해 화면이 지나치게 복잡해지지 않도록 한다.

먼저 현재 작업 트리와 관련 소스코드를 확인해줘. 이 지시문 작성 시점의 GitHub `main`에는 `pitch.py`가 없었으므로, 이미 작업 중인 브랜치에 F0 구현이 추가되어 있다면 기존 구현을 확인하고 재사용해줘. 중복 모듈이나 중복 계산을 만들지 마.

## 2. 최종 사용자 화면 순서

다음 순서를 기준으로 화면을 구성해줘.

### ① 문장 인식 결과 · Whisper

기존 `_show_result()`의 결과 카드 구조를 유지해줘.

표시 요소:

- 단어 오류율(WER)
- 글자 오류율(CER)
- 바뀜(Substitution), 빠짐(Deletion), 더해짐(Insertion) 개수
- 녹음 품질 상태 칩: 음량, 무음 구간, 클리핑
- Whisper 인식 문장 및 인식 소요 시간

제목은 `문장 인식 일치도 · Whisper`로 정리하는 것을 추천해.

반드시 다음 설명을 포함해줘.

> 이 결과는 녹음된 음성을 문자로 인식한 뒤 기준 문장과 비교한 오류율이야. 발음 정확도 자체를 평가하는 점수는 아니야. Whisper가 문맥으로 잘못된 발음을 보정해 인식했을 수도 있어.

WER/CER는 낮을수록 좋은 오류율이라는 점을 유지해줘. 단어를 공백으로 구분하지 않는 언어는 기존 언어별 채점 규칙에 따라 글자 대조 결과를 보여줘.

녹음 품질 칩과 경고는 점수와 구별해줘. 입력 상태 안내이지 발음 점수가 아니야.

### ② 단어·글자 대조

현재 `web_practice.diff_html()`을 활용하는 구조를 유지해줘.

표시 요소:

- 위쪽: 기준 문장
- 아래쪽: Whisper가 인식한 사용자 발화
- 바뀐 부분: 보라색, 물결 밑줄, `바뀜` 표시
- 빠진 부분: `빠짐` 표시
- 추가된 부분: `더해짐` 표시
- 일치한 부분: 일반 텍스트

언어에 따라 제목은 `단어 대조` 또는 `글자 대조`로 구분해줘.

기존 색상뿐 아니라 밑줄 및 텍스트 라벨로 오류 종류를 구분하는 방식은 유지해줘.

### ③ 다시 듣기

현재 구현된 TTS와 사용자 녹음 재생 기능을 유지해줘.

표시 순서:

1. 표준 발음 · TTS
2. 내 녹음

두 음성을 각각 명확하게 구분해줘. 모바일에서도 재생 컨트롤과 설명이 복잡해지지 않도록 현재 Streamlit audio player를 활용해줘.

### ④ 틀린 구간 확인

현재 `_show_error_spans()`와 `visualisation.plot_error_spans()`를 유지해줘.

현재 시각 요소:

- 왼쪽: 표준 발음(TTS)
- 오른쪽: 사용자 녹음
- 첫 번째 행: 파형
- 두 번째 행: STFT
- 세 번째 행: Log-Mel
- 파형 위에 단어와 시작 시간 표시
- 오류가 발생한 덩어리를 `[1]`, `[2]` 등 같은 번호로 양쪽에 표시
- 동일한 번호는 기준 음성과 사용자 음성에서 대응되는 오류 덩어리

기존 안내 문구를 유지하거나 다음과 같이 정리해줘.

> 같은 번호는 기준 음성과 내 녹음에서 대응하는 오류 구간이야. 구간은 Whisper가 추정한 단어 시간으로 표시하므로 정확한 강제 정렬은 아니야. 이 그림은 오류가 발생한 위치를 보여주지만 발음 오류의 원인까지 진단하지는 않아.

오류가 없으면 다음 안내를 표시해줘.

> 인식 결과가 기준 문장과 같아서 표시할 오류 구간이 없어.

표준 발음이 없는 경우에도 현재의 안내 흐름을 유지해줘.

### ⑤ 목소리 높낮이 비교 · F0 contour

이번 작업에서 추가할 핵심 기능이야.

#### 화면 제목

`목소리 높낮이 비교 · F0 contour`

#### 그래프 구성

- 하나의 그래프에 TTS와 사용자 음성의 F0 contour를 중첩한다.
- TTS는 기존 초록 계열, 사용자 음성은 보라 계열을 사용한다.
- 기존 `theme.py`의 색상 팔레트를 재사용한다.
- y축은 Hz가 아니라 상대 음높이(semitones)를 표시한다.
- x축은 기준 문장의 단어 순서에 맞춘 구간으로 구성한다.
- 단어별 구간은 배경 영역 또는 구분선으로 구분하고 단어 이름을 표시한다.
- 각 음성의 무성음 구간은 0Hz로 표시하지 않고 그래프 선을 끊는다.
- 범례에는 `참고 TTS`, `내 녹음`을 표시한다.
- 수치 점수, 등급, 합격·불합격 표시를 추가하지 않는다.

#### 상대 F0 계산

각 음성의 중앙 F0를 각각 계산하고 다음 공식을 사용해 정규화한다.

R_s(t) = 12 × log2(F0_s(t) / median(F0_s))

여기서:

- s: TTS 또는 사용자 음성
- F0_s(t): 해당 음성의 시점별 F0
- median(F0_s): 해당 음성의 유성 프레임 F0 중앙값

유효한 유성 프레임만 중앙값 계산에 사용해줘. 무성음, 무음, NaN, 무한대, 0 이하 값은 계산 대상에서 제외해줘.

두 화자의 절대적인 음높이 차이가 아니라 각자의 기본 음높이에서 얼마나 상승하거나 하강하는지를 비교하는 것이 목적이야.

#### 단어별 x축 정렬

두 음성의 발화 속도와 단어별 지속시간은 다를 수 있어.

따라서 단순히 TTS와 사용자 녹음의 실제 초 단위 시간을 그대로 겹쳐서 비교하지 마.

현재 `stt.recognize_words()`는 각 단어의 `start`, `end`, `prob`를 반환하고, `align.py`에는 `word_tokens()` 및 `locate_errors()`가 있어.

가능하면 이 기존 로직을 활용해 기준 문장에 대한 TTS 단어 및 사용자 단어의 대응 관계를 확보해줘.

MVP에서는 다음과 같이 처리해도 돼.

- 기준 문장의 단어 순서를 공통 x축으로 사용한다.
- 각 음성에서 해당 단어의 실제 발화 구간을 확보한다.
- 각 단어 구간 내부의 시간 진행률을 공통 단어 구간에 매핑한다.
- 동일한 단어의 TTS contour와 사용자 contour가 같은 x축 구간에 오도록 한다.
- 대응 단어가 없는 경우 해당 구간은 비워둔다.
- 강제 정렬이나 DTW 등 새로운 복잡한 정렬 알고리즘을 추가하지 않는다.

이 방식은 단어 내부의 발화 시간 차이를 정규화하는 것이므로, 원래의 실제 말하기 속도나 음소별 타이밍 차이를 비교하는 기능은 아니라는 점을 인지해줘.

정렬이 불확실한 경우에는 정확히 정렬된 것처럼 표현하지 말고 해당 단어 구간을 생략하거나 안내해줘.

#### 계산 재사용 및 성능

현재 `wp.error_spans()` → `practice.locate_errors()` → `stt.recognize_words()`는 오류 구간을 계산하기 위해 TTS와 사용자 음성을 다시 인식해.

F0 비교에서도 동일한 두 음성의 단어별 시간이 필요하므로 Whisper 인식을 중복 실행하지 않도록 구조를 검토해줘.

가능하면 한 번 확보한 TTS/사용자 단어별 시간 및 정렬 결과를 다음 두 기능이 공유하도록 해줘.

- 틀린 구간 표시
- F0 contour 비교

오류가 없는 경우에도 F0 그래프를 만들 수 있어야 해. 현재 오류 구간 기능은 오류가 있을 때만 계산되므로, F0 분석에 필요한 단어 정렬을 별도로 확보할 수 있도록 조정해줘.

#### F0 설명 문구

그래프 바로 아래에 다음 설명을 표시해줘.

> 두 음성의 기본 음높이 차이를 줄이기 위해 각 음성의 중앙 F0를 기준으로 상대적인 음높이를 표시해. 같은 단어에서 두 선이 어떻게 상승하거나 하강하는지 관찰해 봐. 이 그래프는 억양의 음향적 차이를 살펴보기 위한 참고 정보이며, 발음 점수는 아니야.

반드시 다음 사항을 지켜줘.

- TTS의 억양이 유일한 정답이라고 표현하지 않는다.
- 의문문은 항상 끝을 올려야 한다고 안내하지 않는다.
- 상대 F0 상승량이 크다고 발음이 더 좋다고 평가하지 않는다.
- F0를 자음·모음의 조음 정확도를 판정하는 데이터로 설명하지 않는다.
- 사용자와 TTS의 절대 F0 차이를 발음 오류로 해석하지 않는다.

#### 표시 조건

- 따라읽기 모드에서만 표시한다.
- 두 음성의 유효한 F0 분석 결과가 있으면 중첩 그래프를 표시한다.
- TTS가 준비되어 있지 않으면 사용자 F0만 보여주거나 TTS가 있어야 비교할 수 있다는 안내를 제공한다.
- 유효한 유성 프레임이 부족하거나 분석에 실패해도 WER/CER와 Azure 결과는 정상적으로 표시되어야 한다.
- 중국어·일본어 등 단어 분리 방식이 다른 언어는 현재 MVP의 단어별 정렬을 무리하게 적용하지 말고, 지원 조건을 명확하게 처리해줘.
- F0는 사용자 녹음에 대한 참고용 분석으로만 사용한다. 이번 MVP에서는 DB 저장, 기존 scoring JSON 변경, Azure JSON 변경, 스키마 마이그레이션을 하지 않는다.

### ⑥ Azure 발음 평가

현재 `_show_azure()` 기능은 유지하되 표시 제목을 다음처럼 정리해줘.

`Azure 발음 평가 · 외부 서비스 · 선택`

기존 기능:

- 사용자가 버튼을 눌렀을 때만 Azure Speech로 녹음, 기준 문장, 로캘을 전송
- TTS 음성은 전송하지 않음
- 정확도, 유창성, 완성도, 운율, 종합 점수 카드
- 단어별 정확도
- 영어(en-US)의 경우 음소별 IPA 정보 펼침
- 언어별로 제공되지 않는 항목은 기존 안내 유지

기존 점수와 계산 로직을 수정하지 마.

외부 전송 안내 문구는 Azure 버튼보다 위에 표시해줘.

> 버튼을 누르면 내 녹음과 기준 문장, 언어 정보가 Microsoft Azure Speech로 전송돼. 표준 발음(TTS) 음성은 전송하지 않아. Azure 발음 평가 모델을 이용하는 선택 기능이야.

Azure는 자동 실행하지 말고 반드시 사용자가 버튼을 눌렀을 때만 실행해줘.

### ⑦ 소리 모양 자세히 보기

현재 `_show_sound_shapes()`의 네 가지 시각화는 유지하되, 기본 화면을 간결하게 만들기 위해 접힌 상태의 `st.expander` 안에 배치하는 것을 추천해.

제목:

`소리 모양 자세히 보기 · 음향 시각화`

현재 2×2 배치 유지:

- 파형
- FFT
- STFT
- Log-Mel

각 항목의 부가 설명도 유지해줘.

| 항목      | 설명                       |
| ------- | ------------------------ |
| 파형      | 시간에 따른 소리 크기(진폭)와 타이밍    |
| FFT     | 소리 전체의 주파수별 크기(시간 정보 없음) |
| STFT    | 시간에 따른 주파수별 파워           |
| Log-Mel | 시간에 따른 Mel 주파수 영역의 로그 파워 |

기존 `SOUND_SHAPE_GUIDE`를 활용하되 새 F0 기능과 역할이 혼동되지 않도록 설명을 조정해줘.

특히 다음 내용을 명확하게 유지해줘.

- 파형은 음량 비교용 점수가 아니다. 현재처럼 두 음성의 최대 진폭을 정규화한 결과다.
- FFT는 시간에 따른 음높이 변화를 보여주지 않는다.
- FFT의 가장 큰 주파수 봉우리가 반드시 F0인 것은 아니다.
- STFT와 Log-Mel은 음향 에너지의 시간·주파수 분포를 보여주며 발음 정확도 점수가 아니다.
- 두 음성의 실제 시간축은 서로 다를 수 있다. 단어별 정렬을 보장하는 그래프로 설명하지 않는다.

역할을 최대한 기존 구조에 맞춰 분리해줘.

- F0 계산은 전용 분석 모듈(예: `pitch.py`)
- 그래프 렌더링은 `visualisation.py`
- 결과 상태와 배치는 `app/ui_practice.py`
- 단어 시간 및 정렬은 기존 `stt.py`, `align.py` 로직을 재사용
- 오디오 로딩은 기존 `audio.load_audio()` 활용

기존 기능의 의미를 변경하지 마.

- WER/CER 계산 변경 금지
- Azure 평가 기준 및 점수 변경 금지
- Azure 자동 호출 금지
- 기존 녹음 저장·기록 흐름 변경 금지
- F0 DB 저장 및 스키마 변경 금지
- F0 오류가 전체 채점 결과에 영향을 미치지 않도록 처리

예외가 발생하면 F0 영역에만 안내를 표시하고 나머지 결과는 정상적으로 보여줘.

## 5. 테스트 및 완료 기준

다음 사항을 확인해줘.

1. 정상적인 영어 문장 녹음에서 기존 WER/CER 결과가 변경되지 않는다.
2. 단어 오류가 있으면 기존 오류 구간 시각화가 정상적으로 작동한다.
3. 오류가 없어도 TTS와 사용자 음성의 F0 contour 비교가 가능하다.
4. 두 음성의 중앙 F0가 다른 경우에도 상대 semitone 기준 그래프가 정상적으로 표시된다.
5. 무성음 구간은 그래프에서 끊겨 표시된다.
6. 너무 짧거나 무성음뿐인 녹음에서 예외가 발생해도 기존 채점 결과는 유지된다.
7. TTS가 없을 때 적절한 안내를 표시한다.
8. Azure는 버튼을 누르기 전까지 호출되지 않는다.
9. F0 분석 실패가 Azure 분석에 영향을 주지 않는다.
10. 기존 파형·FFT·STFT·Log-Mel 그래프가 유지된다.
11. 모바일 화면에서도 그래프와 텍스트가 읽기 쉽게 표시된다.
12. `st.session_state`를 이용한 결과 보관 및 `건너뛰기` 초기화가 정상적으로 작동한다.
13. 기존 DB 구조와 저장 기능에 불필요한 변경이 없다.

마지막으로 변경된 파일, 구현 내용, 실행한 테스트, 아직 남은 한계를 요약해줘.

**이번 작업의 핵심은 평가 항목을 많이 보여주는 것이 아니라, 사용자가 `내가 무엇을 다르게 발음했는가 → 어디서 차이가 발생했는가 → 억양은 어떻게 달랐는가 → 다음에는 무엇을 바꾸어 볼 것인가`를 순서대로 이해하도록 만드는 것이야.**

이렇게 구현하면 SongLingo의 결과 화면은 단순한 점수판에서 벗어나 문장 인식 결과, 오류 위치, 음향적 억양 관찰, 선택적 발음 평가를 연결하는 학습 피드백 화면이 될 거야. 특히 F0를 추가해도 기존 WER/CER와 Azure의 역할을 침범하지 않는다는 점이 중요해.
